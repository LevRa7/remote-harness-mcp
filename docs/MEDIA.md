# `read_media`: файл уходит в чат блоком MCP, а не сырыми байтами

`read_file` отвечает текстом с номерами строк — это правильная форма для исходников
и логов и неправильная для всего, что человек реально присылает: скриншот, фотография,
PDF, голосовое сообщение, клип. Протокол MCP для таких данных придумал отдельные
блоки — `image` (base64 + `mimeType`), `audio` (то же самое) и `text`, — и `read_media`
единственное место в проекте, которое решает, каким блоком станет файл, сколько его
поместится и что сказать, когда не помещается ничего.

## Что приходит в ответе

Инструмент возвращает **массив контент-блоков**. Первый блок — всегда `text` с
описанием файла (имя, MIME, размер, что именно с ним сделали и почему); за ним идут
блоки с содержимым. Ни шлюз, ни `core/server.py` больше ничего не переупаковывают:
`content` собирается на узле и передаётся клиенту дословно.

```json
{
  "type": "image",
  "data": "iVBORw0KGgoAAAANSUhEUg…",
  "mimeType": "image/png"
}
```

Ответ `read_media` в форме результата инструмента:

```json
{
  "ok": true,
  "kind": "image",
  "content": [
    {"type": "text",  "text": "[VERIFIED BY TOOL] read_media: …\\desktop.png\nimage: 2520x1680 sent as 1260x840 image/png (59.3 KiB base64)"},
    {"type": "image", "data": "iVBORw0KGgo…", "mimeType": "image/png"}
  ],
  "meta": {"mime": "image/png", "image": {"action": "downscaled", "sent_pixels": [1260, 840]}},
  "warnings": [],
  "truncated": false, "next_cursor": null
}
```

## Маршрутизация по типу

| Тип (по сигнатуре, расширение — только подсказка) | Блок | Что делает конвертер |
| :--- | :--- | :--- |
| `image/png` | `image` | Декодируется и ужимается на чистом Python (box-фильтр по целому коэффициенту), перекодируется тем же PNG-энкодером, что и скриншоты. Уже маленькая картинка уходит байт-в-байт. |
| `image/jpeg`, `image/webp`, `image/gif`, `image/bmp`, `image/tiff` | `image` | Только измеряется по заголовку. Если байт мало — уходит как есть; если много или шире лимита — ужимается через `ffmpeg` в JPEG (`-q:v 4`). |
| `application/pdf` | `text` (+ `image`) | Текст страниц через PyMuPDF → pypdf → `pdftotext` → встроенный разбор потоков. Если текстового слоя нет (скан), страницы рендерятся в PNG/JPEG через PyMuPDF или `pdftoppm`. |
| `audio/*` (`wav`, `mp3`, `ogg`, `flac`, `m4a`) | `text` (+ `audio`) | WAV читается модулем `wave`, MP3 — по кадровому заголовку, остальное — `ffprobe`. Блок `audio` отправляется **только** при `include_audio=true` и только если файл влезает в бюджет. |
| `video/*` (`mp4`, `mkv`, `avi`, `mov`, `webm`) | `text` + `image` | `ffprobe` даёт длительность, кодек и разрешение; `ffmpeg` нарезает равномерно `max_frames` кадров (`fps = кадры / длительность`) и ужимает их до `max_side`. |
| `text/*`, `application/json`, `*.csv`, `*.log`, `*.md`, исходники | `text` | Кодировка определяется по BOM и содержимому, управляющие символы и ANSI-последовательности вырезаются, текст отдаётся страницей с `cursor`. |
| архив (`zip`, Office) | `text` | Не распаковывается: ответ объясняет, что делать (`bash_exec` + `unzip`, конвертация в PDF) и чем поможет `share_file`. |
| прочее | `text` | «binary: у этого файла нет текстового слоя» + первые 16 байт + подсказка `share_file`. |

## Бюджеты

Base64 на треть больше исходных байт, а ответ читает модель с контекстным окном, поэтому
каждый вызов ограничен — и каждый обрез назван в текстовом блоке, а не спрятан:

| Параметр | По умолчанию | Зачем |
| :--- | :--- | :--- |
| `max_bytes` (файл) | 30 МиБ | Больше — работа для `share_file`: читать 200 МБ в память узла бессмысленно. |
| `max_side` (картинка) | 1280 px | Скриншот 2520×1680 после ужатия занимает 59 КБ base64 вместо 251 КБ. |
| `max_image_bytes` | 700 КиБ | Верхняя граница одной картинки; если PNG не влез даже после двух дополнительных ужатий, ответ об этом говорит. |
| `max_frames` | 4 | Кадры видео и страницы сканированного PDF. |
| `max_total_b64` | ~2,6 МБ | Весь ответ целиком. Блоки считаются **до** добавления, поэтому «шесть кадров по 400 КБ» не превратятся в ответ, который клиент молча отбросит. |
| `max_chars` | 24000 | Текст и текст PDF. Дальше — `cursor=next_cursor`. |
| `include_audio` | `false` | Узел не знает, принимает ли клиент аудио: по умолчанию отправляются только метаданные. |

У шлюза есть свой предохранитель — 12 МиБ base64 на ответ (`MAX_GATEWAY_MEDIA_B64`):
он нужен, если узел старый или сломанный, и никогда не срабатывает на нормальном ответе.

## Кодировки текста

Порядок: BOM (`UTF-8`, `UTF-16`, `UTF-32`) → `utf-8` → `cp1251` (если после декодирования
текст действительно кириллический) → `cp1252` (Windows Western) → `latin-1` (последним,
потому что он не падает никогда). Явный `encoding` в аргументах имеет приоритет.

Это важно именно на Windows: один и тот же узел встречает `cp866` из консоли, `cp1251`
из старых программ и `utf-8` из git. `read_file` открывает файл с `errors="replace"` —
для исходников это нормально, для русского лога это стена символов `�`, из которой модель
ничего не восстановит.

## Опциональные бэкенды и честная деградация

Узел ставится на чистую систему, поэтому обязательных зависимостей нет: всё, что требует
сторонних программ, ищется при вызове, а его отсутствие меняет **ответ**, а не ломает вызов.

| Бэкенд | Что даёт | Без него |
| :--- | :--- | :--- |
| `ffmpeg` (+`ffprobe`) | Кадры видео, ужатие больших JPEG/WebP/GIF, точные метаданные аудио и видео | Видео: только метаданные и подсказка `winget install Gyan.FFmpeg`; фото больше 700 КиБ: объяснение и `share_file` |
| PyMuPDF (`pymupdf`) | Точный текст по страницам и рендер страниц | Текст: pypdf → `pdftotext` → встроенный разбор; рендера страниц нет |
| pypdf | Текст по страницам без системных пакетов | Следующий бэкенд |
| `pdftotext` / `pdftoppm` (poppler) | Текст и рендер без Python-пакетов | Следующий бэкенд / без рендера |
| — (стандартная библиотека) | PNG-декод и ужатие, WAV, MP3-заголовок, текст | — |

Пути к бинарям можно задать явно, не трогая PATH машины: `MESH_FFMPEG`, `MESH_FFPROBE`,
`MESH_PDFTOTEXT`, `MESH_PDFTOPPM`.

Рабочий каталог для выходных файлов `ffmpeg` — в кэше узла (`MESH_CACHE_DIR`, иначе
`~/.cache/remote-harness-mcp/media/work`), а не в системном `%TEMP%`: у службы Windows
свой временный каталог, к которому её учётная запись может не иметь доступа, а контейнер
и песочница вообще не пишут за пределы смонтированного тома. Каталог создаётся через
`os.makedirs`, а **не** `tempfile.mkdtemp`: на Windows `mkdtemp` пишет DACL `0o700`, после
которого дочерний `ffmpeg` не может открыть собственный вывод (проверено: `WinError 5`).

## Почему не ссылка и не `read_file`

* **Ссылка** (`share_file`) нужна человеку: открыть в браузере. Модель по ссылке файл не
  увидит — она увидит строку URL. Поэтому ссылка остаётся запасным вариантом, а не основным.
* **`read_file`** на PNG или PDF вернёт либо мусор, либо ошибку: он читает текст и нумерует
  строки. Для медиа нужен инструмент, который отдаёт блок.

## Безопасность

* Инструмент **только читает**: он объявлен `readOnlyHint: true` на обеих сторонах, входит
  в `_READ_ONLY_ALLOWED` и `policy.READ_ONLY_TOOLS`, поэтому работает и в режиме наблюдения —
  ровно тогда, когда оператору нужно посмотреть скриншот.
* Путь проходит через общий `_resolve()`: в изолированном контейнере — только смонтированный
  проект, иначе — абсолютный путь или путь от рабочего каталога узла.
* Лимиты стоят **до** чтения (`max_bytes`) и **до** добавления блока (`max_total_b64`), так что
  один вызов не может ни съесть память узла, ни переполнить ответ клиента.
* Текстовые блоки очищаются от управляющих символов и ANSI-последовательностей: JSON-RPC
  допускает их экранированными, но модель на них только тратит контекст.

## Проверка

```bash
# на узле
python -c "from core import media; r = media.read_media(r'C:\\Pictures\\screen.png'); print([b['type'] for b in r['content']])"
```

Через MCP: `tools/call` с `{"name": "read_media", "arguments": {"path": "…"}}` — в ответе
должен быть массив `content` из блоков `text`/`image`/`audio`.

Тесты: `tests/test_read_media.py` (22 теста) — фикстуры строятся в самом тесте: PNG пишет
собственный энкодер проекта, WAV — стандартная библиотека, PDF — пять объектов с
несжатым потоком, чтобы встроенный фолбэк проверялся и на машине без PDF-библиотек.


## Почему Gemini не видит картинку (и при чём тут не узел)

Проверено 24.11.2026 на живом узле: `read_media` отдаёт блок ровно по спецификации
(`{"type": "image", "data": "<base64>", "mimeType": "image/png"}`), байты блока
совпадают с файлом бит-в-бит, но модель отвечает «изображение не передалось».

Причина не в сервере, а в канале ответов инструментов: в Gemini API часть
`functionResponse` несёт только текст и структурированные данные; картинку модель
получает лишь как отдельную часть **запроса** (`inlineData`), которую прикладывает
клиент. Значит клиент должен вынуть картинку из ответа инструмента и добавить её в
следующий запрос — этого он пока не делает. Это известное ограничение:
[google-gemini/gemini-cli#2136](https://github.com/google-gemini/gemini-cli/issues/2136)
открыт с июня 2025, и последний комментарий (19.12.2025) — «still doesn't work».
Наш блок ничего не нарушает: его просто выбрасывают.

Что из этого следует:

* порядок блоков изменён на «картинка первой» (`media.read_media`) — на случай, если
  клиент смотрит только на первый блок; это дешёвая проверка, а не решение;
* **OCR** остаётся как опция (`"ocr": true`) для скриншотов, документов и
  сканированных PDF — это не замена мультимодальности, а способ вытащить текст,
  когда картинка не доходит; по умолчанию выключен, чтобы не платить задержкой;
* реальные пути получить «модель увидела картинку»: другой MCP-клиент (Claude
  Desktop/Code, Cursor и т. п. поддерживают `image`-блоки) или vision-вызов на узле
  (узел сам отправляет картинку в Gemini API и возвращает в чат понятный ответ).
  Второй вариант — отдельная зависимость и ключ, но он даёт настоящее понимание
  изображения, а не текст с него.

### Если всё же нужен OCR

| Способ | Команда | Замечания |
| :--- | :--- | :--- |
| Windows OCR | `py -3 -m pip install winsdk` | `Windows.Media.Ocr`, языки из системы (`ru`, `en-US`), узел сам находит `tools/ocr_windows.py` |
| Tesseract | `winget install UB-Mannheim.TesseractOCR` | языки `rus+eng`; путь переопределяется `MESH_TESSERACT` |
| Свой движок | `set MESH_OCR_CMD=python D:\path\ocr.py` | команда получает путь к картинке последним аргументом, печатает текст в stdout |

Приоритет: `MESH_OCR_CMD` → tesseract → `tools/ocr_windows.py`. Включается
`"ocr": true` в вызове `read_media`.

## Ограничения

* Распознавания речи на узле нет: аудио отдаётся метаданными (или блоком `audio`), а
  транскрипцию надо добавлять отдельным шагом (`faster-whisper`) — ответ так и говорит.
* JPEG без `ffmpeg` не перекодируется: свой JPEG-кодек не тащим, поэтому большая фотография
  либо уходит как есть (если влезает в бюджет байт), либо получает объяснение и `share_file`.
* Офисные форматы (`docx`/`xlsx`/`pptx`) не распаковываются: это архив, ответ предлагает
  конвертировать в PDF или распаковать `bash_exec`.
* Анимированный GIF — это `image/gif` без раскадровки: клиент покажет то, что покажет.
