# Remote Harness MCP 0.4.7 — rotate the device token without reinstalling the node

Until now the only way to replace a leaked device token was to reinstall the node,
which threw away its name, its link key and its job history. `0.4.7` replaces that
advice with one command that works on every platform the node runs on.

## One command

```bash
remote-harness-mcp rotate          # through the npm CLI
python -m core.rekey               # or straight from the install directory
```

```
device token rotated for 'matebook-deb' on https://mesh.example.com
  updated /home/lev/.config/remote-harness-mcp/agent.env
  restarted via systemd rhm-agent.service
the previous token is now invalid; the link key in MCP URLs is unchanged
```

Useful flags: `--dry-run` (show the files it would touch), `--json`, `--timeout`,
`--no-restart`, `--gateway`, `--user`, `--token`, `--config-file`.

## What it does, in order

1. **Checks the node is online.** Rotating a node you cannot verify is how people
   lock themselves out.
2. **Asks for a new token** with the current one: `POST /v1/devices/<node>/rotate-token`.
3. **Writes it everywhere the token lives**:
   - `agent.env` on every platform;
   - the launchd plist on macOS;
   - the Startup `.vbs` on Windows.
   The last two bake the value into their own files, and on Windows that launcher
   exports `MESH_TOKEN` into the agent's environment - so an env file-only rotation
   would quietly undo itself at the next logon.
4. **Restarts whatever supervises the agent**: `systemctl --user restart rhm-agent`,
   `launchctl kickstart -k gui/<uid>/com.remoteharness.mcp.agent`,
   `schtasks /Run /TN RemoteHarnessMCPWatchdog` (after stopping the old process),
   or `sv restart rhm-agent` under Termux. A payload without a supervisor falls
   back to starting the agent directly.
5. **Waits for the gateway to report the node online** (60 s by default).
6. **On failure, puts the old token back everywhere and restarts again.**

## Why the old token still works for a moment

The rotation is deliberately two-phase. The gateway stores the new token as
*pending* and keeps accepting the current one until the node opens a tunnel with
the new one - the only proof that the secret actually reached the configuration.
If the agent fails to restart, step 6 restores the old token and nothing is lost.

When the token is known to be in someone else's hands and waiting is not an option:

```bash
curl -sX POST https://<gateway>/v1/devices/<node>/rotate-token/finish \
  -H "X-Admin-Token: $MESH_ADMIN_TOKEN"
```

The previous token dies immediately; the node will need the new one applied by
hand (the command above prints it).

## Notes

- Rotating the **device token** does not touch the **link key** in MCP URLs, and
  rotating the link key (`POST /v1/devices/<node>/rotate`) does not touch the
  tunnel credential. They are separate on purpose: a leaked URL should not force
  a restart, and a leaked tunnel token should not force you to re-paste a link
  into Gemini.
- `rotate-token` needs the node's current token or `MESH_ADMIN_TOKEN`; the link
  key is not accepted, because it can run tools but must not be able to replace
  the machine's identity.
- A standalone node (no gateway, no tunnel) has no token to rotate and says so.
- `revoke` remains the option of last resort: it removes the node and closes its
  tunnel.
