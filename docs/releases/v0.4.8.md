# Remote Harness MCP 0.4.8 — updating or reinstalling keeps your token and your URL

A compatibility fix on top of 0.4.7, prompted by a fair question: *does the token
change when I update or reinstall?*

## The short answer

| Action | Device token | The MCP URL already in Gemini |
| :--- | :--- | :--- |
| `mesh_update` / automatic update | unchanged | keeps working |
| Re-running the installer **with the existing config** | unchanged (the gateway echoes the token the node proves) | keeps working — from this release |
| Reinstalling **without** the config, or under a new name | new token, name may get `-2` | dead: it addresses a node that no longer has those credentials |
| `rotate` (link key) | unchanged | the `lk_…` URL is replaced; a legacy device-token URL still works |
| `rotate-token` (device token) | new | dead by design, and the node must apply the new token |

## What was wrong in 0.4.6 and 0.4.7

Upgrading a pre-0.4.6 node to a link key also cleared the "legacy URL" allowance,
so the **same token** stopped being accepted in the query string the moment the
node re-registered. The installer printed a fresh `lk_…` URL, but the connector
already pasted into Gemini kept the old one and quietly started failing — with
the token unchanged, which made it look like a gateway problem.

From this release the upgrade only *adds* a link key:

- the node's existing URL keeps working (the token is stored as a hash now, and
  it still verifies);
- the installer's new `lk_…` URL works as well;
- `rotate-token` is the only command that ends the old credential, and it does so
  only after the node has connected with the replacement;
- `rotate` (link key) retires the link URL alone, because rotating a leaked link
  should not force anyone to change the tunnel credential.

A plaintext token from a pre-0.4.6 registry is still moved to its hash — first on
re-registration, and now also on a link-key rotation, which previously dropped the
plaintext without keeping a hash and so invalidated the old URL by accident.

## If a reinstall did mint a new name

Registration only reuses a name when the request proves possession of that node's
token. Without it the gateway returns 409, or — when the installer asks for
`auto_suffix` — allocates `name-2` with new credentials. That is what leaves an old
connector pointing at a dead name. Either paste the URL the installer printed, or
keep `agent.env` (it carries `MESH_USER` and `MESH_TOKEN`) across the reinstall.

## Upgrading

Nothing to do on the node beyond the normal update; the gateway change is what
matters and it is backward compatible in both directions.
