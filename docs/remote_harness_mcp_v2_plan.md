## 1. Резюме

### 1.1. Что меняется

Сейчас Remote Harness MCP — это **транспорт**: узел ставится на машину, поднимает исходящий WS-туннель к шлюзу, шлюз отдаёт MCP-эндпоинт облачному агенту. Есть зрелые кирпичи: два типа ключей (device token + link key), pairing, ротация токена, read-only на узле, аннотации инструментов, шары файлов, автообновление, установщики под Windows/Linux/macOS/Android.

Запрос превращает продукт в **платформу управления устройствами**:

| Слой | Что появляется |
| :--- | :--- |
| Устройство | Трей-приложение: меню, пульсация, запросы разрешений, журнал, режим Read-only/Agent, рабочая папка |
| Аккаунт | Кабинет: устройства, агенты, статистика, переименование, отключение, удалённые команды, файлы, права |
| Подключение | Онбординг: выбор облачного агента (Gemini/Claude/GPT), автоподстановка MCP-адреса, OAuth-авторизация |
| Доставка | LiveUSB с автоподбором драйверов и Wi-Fi-мастером, Docker-образ, self-host установщик |
| Федерация | Свой мост с Google-аккаунтом, миграция устройств, fallback на публичный мост |
| Крипто | E2E-модель, при которой недобросовестный self-host оператор не читает данные клиентов |

### 1.2. Четыре архитектурных решения, от которых зависит всё

1. **Edge (вендорный краевой сервис) как стабильная точка входа.** Один URL вида `https://<edge>/d/<device-id>/mcp` на устройство, который не меняется при переезде с публичного моста на self-host, при падении моста и при смене домена. Edge терминирует TLS для облачных клиентов, ведёт OAuth-авторизацию и маршрутизирует вызов на активный мост. Без edge фичи 10–12 (миграция, fallback, «один адрес навсегда») стоят дорого и работают плохо.
2. **Аккаунт и агент — разные сущности.** `Account` (Google) владеет устройствами; `AgentConnection` — это конкретный облачный агент/клиент (Gemini, Claude, GPT, Claude Code, Cursor), у которого свои права, режим, рабочая папка и статистика. Link key остаётся, но превращается в «legacy-вход», привязанный к записи агента.
3. **Локальный Control API на узле + отдельное трей-приложение.** Агент (Python) отдаёт состояние и события по локальному сокету с токеном; трей (Avalonia/.NET) рисует иконку, меню и hover-панель. Это разделяет «движок» и «UI», позволяет делать UI на трёх ОС и не тащить GUI в Python-процесс.
4. **Два режима доверия моста.** `blind` (рекомендуется для self-host): MCP-сервер живёт на устройстве, edge шифрует трафик до устройства (Noise), мост — только релей, видит шифротекст. `terminating`: MCP-сервер на мосту, live-трафик виден оператору; это допустимо только с явным предупреждением и компенсирующими мерами. Фича 13 — это в первую очередь выбор режима и ключевая иерархия, а не «шифрование всего подряд».

### 1.4. Главный риск

Несовместимость облачных клиентов с OAuth и отсутствие у части из них поддержки remote MCP. Поэтому **link-key URL сохраняется как первый класс** на весь переходный период: любой сценарий онбординга должен работать и без OAuth, а OAuth — улучшать, а не заменять.

### 1.5. Что не входит в этот план

- Биллинг, тарифы, лимиты и продажи.
- Мобильные нативные приложения (только адаптивные веб-страницы).
- Полноценный MDM (инвентаризация софта, политики ОС, antivirus).
- Потоковый remote desktop (существующий `device_capture` — снимки/запись, не видео).
- Сертификация SOC 2 / ISO 27001 (закладываем требования, но не проходим в рамках проекта).
- Поддержка 24/7 и SLA-процессы.

### 1.6. Первые шаги (2 недели)

1. **ADR-001:** edge как обязательный/опциональный компонент; зафиксировать влияние на self-host.
2. **ADR-002:** режимы доверия `blind` / `terminating`; что обещаем в каждом.
3. **ADR-003:** модель `Account/Tenant/Device/AgentConnection`; миграция `registry.json`.
4. **Spike OAuth (2–3 дня):** DCR + PKCE с Claude и ChatGPT; проверить, что реально поддерживается, записать матрицу.
5. **Spike Noise-over-WS (2 дня):** замерить overhead и поведение при реконнекте через релей.
6. **Разрезать `gateway.py`** на пакет `bridge/` без изменения поведения; все существующие тесты зелёные.
7. **`SessionContext`** в `mcp_tools` вместо глобального `_READ_ONLY`; 1258 тестов зелёные.
8. **Control API + токен** и прототип трея (иконка, меню, состояние).
9. **Схема БД + dual-read** `registry.json`; скрипт миграции и отката.
10. **Пилот:** 5 пользователей, 3 устройства (Windows/macOS/Linux), 2 облачных клиента; зафиксировать метрики (время онбординга, p95 вызова, доля ошибок).

### 1.7. Ревизия порядка (2026-11-11)

Принято начинать не с Edge и не с LiveUSB, а с **контура управления**. Первый выпуск **Wave 1 «Аккаунт и контроль»** (8 недель):

1. авторизация человека через Google и привязка устройства;
2. личный кабинет: устройства, агенты, переименование, отключение, права, статистика;
3. локальный журнал использования на устройстве;
4. меню настроек в трее (автозапуск, активность, режим, рабочая папка, журнал, кабинет).

Детальный план, API, схема БД, спринты и приёмка — в [wave-1-auth-account-log-settings.md](wave-1-auth-account-log-settings.md). Wave 1 не требует Edge: кабинет монтируется в существующий шлюз по пути `/account`, что экономит 2–3 недели и не блокирует MCP-транспорт.

**Команда и контроль качества:** роли и RACI — [docs/team/AGENT_TEAM.md](team/AGENT_TEAM.md); 111 деталей с владельцами и тестами — [WBS.md](team/WBS.md) и [OWNERSHIP_MATRIX.md](team/OWNERSHIP_MATRIX.md); тест-план — [TEST_PLAN.md](team/TEST_PLAN.md); протокол доказательств — [VERIFICATION_PROTOCOL.md](team/VERIFICATION_PROTOCOL.md). Покрытие проверяется машинно: `python tools/check_team_coverage.py --strict`.

Дальнейший порядок: **Wave 2** — OAuth для MCP-клиентов, hover/abort, полные approvals, онбординг; **Wave 3** — Edge, alias, миграция и fallback; **Wave 4** — LiveUSB, Docker, self-host; **Wave 5** — blind-режим и E2E-крипто. ### 2.2. Чего нет

- **Аккаунтов и БД.** `registry.json` — плоский файл «имя узла → запись»; пользователей, тенантов и агентов нет.
- **Идентичности агента.** Link key один на узел; нельзя отозвать доступ конкретному Claude, не сломав Gemini.
- **Per-agent режима.** `MESH_READ_ONLY` — глобальная переменная процесса.
- **Трея и локального API.** Есть только служебные скрипты и лог.
- **Статистики.** Ни телеметрии вызовов, ни счётчиков по инструментам.
- **OAuth.** Есть только discovery-заглушка `/.well-known/oauth-protected-resource`; AS/DCR/consent отсутствуют.
- **Self-host федерации.** `deploy_gateway.sh` деплоит «свой шлюз», но без аккаунтов, миграции и привязки к Google.
- **Криптослоя.** Токены хешируются, но данные, шары и логи не шифруются; модели «недоверенный хостер» нет.
- **LiveUSB и Docker.** Нет ни образа, ни сборки.

### 2.3. Вывод

Транспортная часть готова примерно на 60%, продуктовая — на 0–10%. План должен **не переписать работающее**, а надстроить: `gateway.py` → `bridge/` с сохранением всех legacy-маршрутов, `registry.json` → БД с dual-read, `MESH_READ_ONLY` → контекст сессии, link-key → запись агента.

                     └───────────────┬────────────────────────────────────────────┘
                                     │ HTTPS (MCP: SSE / Streamable HTTP), OAuth 2.1
                                     ▼
                     ┌────────────────────────────────────────────────────────────┐
                     │ EDGE (вендор, опционально)                                 │

        └───────────────┬────────────────────┘
                        │ WS-туннель (device token), поверх — Noise (blind)
                        ▼
        ┌────────────────────────────────────────────────────────────┐
        │ NODE (устройство: ПК/ноутбук/сервер/Android)                │

### 3.2. Роли и границы доверия

| Компонент | Кому принадлежит | Что видит | Доверие |
| :--- | :--- | :--- | :--- |
| Edge | Вендор | Метаданные аккаунта, OAuth-токены, маршруты; в blind-режиме — шифротекст до устройства | Доверенный (как и облачный LLM) |
| Bridge public | Вендор | То же, что edge, плюс счётчики; в blind — шифротекст | Доверенный |
| Bridge self-host | Клиент/оператор | Только то, что разрешил режим; в blind — шифротекст и метаданные | **Недоверенный по умолчанию** |
| Node | Пользователь | Всё, что делает | Доверенный |
| Tray/UI | Пользователь | Локальные события | Доверенный |
| Облачный агент | Провайдер LLM | Аргументы и результаты вызовов | Доверенный (иначе он не работает) |

Ключевая фраза для документации: **«недоверенный хостер не читает данные» достижимо только тогда, когда MCP-терминация не находится на его машине.** В blind-режиме она на устройстве; в terminating — на мосту, и тогда честно говорим, что хостер видит live-трафик, а защищаем только данные at-rest, другие тенанты и аудит.

### 3.3. Потоки

**Вызов инструмента (blind).**
`Cloud agent → Edge (TLS) → Bridge (WS-фреймы) → Node (Noise-расшифровка) → mcp_tools → ответ тем же путём`.
Мост не может расшифровать payload; он видит tenant id, device id, размер, время.

**Approval.**
`Node` формирует запрос (команда/действие, превью, срок) → tray показывает → пользователь разрешает/запрещает → `Node` отдаёт результат агенту. Если клиент поддерживает MCP elicitation — используем его; иначе структурированная ошибка `approval_required` + `approval_id` и инструмент `approval_status`.

**Шара файла.**
`Node` шифрует файл случайным DEK, загружает шифротекст в storage моста → ссылка `https://…/s/<id>#k=<base64url>` → браузер расшифровывает WebCrypto. Мост и оператор видят только ciphertext; ключ не уходит на сервер (fragment).

**Миграция на self-host.**
`Account` инициирует → edge выдаёт migration grant (подписанный, короткоживущий) → команда узлу `switch_bridge {url, grant}` → узел подключается к новому мосту → мост валидирует grant у edge → edge помечает устройство перемещённым → старый мост отзывает регистрацию с grace-периодом.

**Fallback.**
`Node` держит primary + fallback; при N ошибках подряд уходит на fallback → edge видит, где узел онлайн, и маршрутизирует `/d/<id>` туда → кабинет и трей показывают баннер; возврат на primary по политике.

### 3.4. Совместимость

- Legacy-маршруты `/sse`, `/mcp`, `/messages?user=&token=` продолжают работать; link key принимается как раньше.
- Старые узлы (0.4.x) подключаются к v2-мосту по старому WS-протоколу; мост определяет версию по `hello` и не требует новых полей.
- `registry.json` читается при старте и импортируется в БД; обратная запись — только для отката.
- Все новые фичи — за фича-флагами (`RHMV2_ACCOUNTS`, `RHMV2_TRAY`, `RHMV2_BLIND`, `RHMV2_FALLBACK`), чтобы можно было выпускать по частям.

## 4. Идентичность, доступ, данные

### 4.1. Модель сущностей

| Сущность | Назначение | Ключевые поля |
| :--- | :--- | :--- |
| `Account` | Человек (Google) | `id`, `google_sub`, `email`, `created_at`, `status` |
| `Tenant` | Изолированный контур данных (личный или org) | `id`, `owner_account_id`, `name`, `plan`, `bridge_id`, `data_region` |
| `Bridge` | Публичный или self-host мост | `id`, `tenant_id`, `kind`, `base_url`, `cert_fpr`, `health`, `last_seen`, `version` |
| `Device` | Устройство с узлом | `id`, `tenant_id`, `name`, `platform`, `arch`, `version`, `pubkey`, `cert_fpr`, `mode`, `status`, `last_seen` |
| `AgentConnection` | Конкретный облачный агент/клиент | `id`, `device_id`, `label`, `client_type`, `oauth_client_id`, `mode`, `workspace`, `scopes`, `created_at`, `last_used_at`, `revoked_at` |
| `Grant` | Разрешение агенту на устройство | `id`, `agent_id`, `device_id`, `scopes`, `mode`, `expires_at`, `created_by` |
| `Session` | Один сеанс MCP | `id`, `agent_id`, `device_id`, `started_at`, `ended_at`, `ip_hash`, `transport` |
| `Approval` | Запрос подтверждения | `id`, `session_id`, `tool`, `preview_enc`, `status`, `expires_at`, `decided_by` |
| `UsageEvent` | Счётчик использования (без payload) | `id`, `tenant_id`, `device_id`, `agent_id`, `tool`, `status`, `duration_ms`, `bytes`, `ts` |
| `Share` | Публикация файла/каталога | `id`, `device_id`, `blob_id`, `key_hash`, `expires_at`, `max_downloads`, `downloads` |
| `AuditEvent` | Событие безопасности | `id`, `tenant_id`, `actor`, `action`, `target`, `ts`, `prev_hash`, `hash` |

### 4.2. OAuth 2.1 для MCP-клиентов

Спецификация MCP для HTTP-транспорта опирается на OAuth 2.1, PKCE, resource indicators (RFC 8707), protected resource metadata (RFC 9728) и authorization server metadata (RFC 8414). Реализуем на edge (и опционально на self-host мосту):

- `GET /.well-known/oauth-protected-resource` — указывает на AS.
- `GET /.well-known/oauth-authorization-server` — метаданные AS.
- `POST /v1/oauth/register` — Dynamic Client Registration, allowlist по `client_name`/redirect URI, лимит.
- `GET /v1/oauth/authorize` — редирект на Google, затем consent-экран (устройство, режим, scopes).
- `POST /v1/oauth/token` — code + PKCE, refresh, короткий access token (15 мин), refresh 30 дней.
- `POST /v1/oauth/revoke` — отзыв.

Scopes:

| Scope | Что разрешает |
| :--- | :--- |
| `device:read` | чтение файлов, `system_info`, `list_dir`, `glob_find`, `grep_search` |
| `device:write` | `write_file`, `edit_file`, `run_job` |
| `device:shell` | `bash_exec` |
| `device:control` | `device_control`, `device_capture`, `device_messages` |
| `files:share` | `share_file`, `serve_dir`, `unshare` |
| `admin` | управление устройством из кабинета (только веб-сессия) |

Токен привязан к `agent_connection_id` и `device_id`; мост проверяет подпись edge (JWKS) и срок. Отзыв агента в кабинете — мгновенный (denylist по `jti` + проверка `revoked_at`).

**Важно:** Gemini Connectors сегодня могут не поддерживать OAuth. Поэтому:
- при первом использовании link-key создаётся `AgentConnection` с `label=Gemini` и дефолтным режимом;
- ссылка остаётся рабочей, OAuth предлагается как «более безопасный» вариант;
- в кабинете оба типа агентов выглядят одинаково и отзываются одинаково.

### 4.3. Идентичность устройства

- При установке узел генерирует **Ed25519 keypair**; приватный ключ — в OS keychain (DPAPI/Keychain/libsecret), публичный уходит на edge при pairing.
- Device token (текущий) остаётся для WS-туннеля; дополнительно узел подписывает `hello` ключом, мост проверяет подпись по зарегистрированному `pubkey`.
- Cert pinning: edge запоминает отпечаток ключа при первом подключении (TOFU) и показывает его пользователю в кабинете; смена ключа — только через подтверждение на устройстве.
- Pairing: текущий `POST /v1/devices/pair` → код → подтверждение в кабинете/на устройстве → выдача ключей. Для LiveUSB — одноразовый код с TTL 15 минут.

### 4.4. Режимы и права

| Режим | Что разрешено | Где включается |
| :--- | :--- | :--- |
| `read_only` | `system_info`, `system_vitals`, `list_dir`, `read_file`, `grep_search`, `glob_find`, `mesh_status`, `share_list` | Трей (ПКМ), кабинет, дефолт для нового агента |
| `agent` | всё, что разрешено scopes и политикой узла | Трей, кабинет, явное подтверждение |

Три уровня принуждения (обязательно все три):

1. **Edge/мост** — фильтрация `tools/list` и отказ на `tools/call` по scope/mode.
2. **Токен** — claims `mode`, `scopes`; мост не доверяет клиенту.
3. **Узел** — `SessionContext` в `mcp_tools`: `mode`, `workspace`, `scopes`; глобальный `MESH_READ_ONLY` остаётся как «жёсткий предохранитель» и имеет приоритет.

Понижение `agent → read_only`:
- новые вызовы отклоняются сразу;
- активные мутирующие джобы либо останавливаются (настройка `kill_on_downgrade`, по умолчанию `true`), либо доигрываются с пометкой в журнале;
- событие пишется в audit.

### 4.5. Хранилище и миграция

- **По умолчанию SQLite** (один мост, до ~100 устройств), **Postgres** — для публичного edge и крупных self-host.
- Миграции — Alembic; при старте — `dual-read`: если есть `registry.json`, импортируем в `Device`/`Tenant` (тенант `legacy`), сохраняя link key и хеш токена.
- Персистентность: `tenants`, `devices`, `agents`, `grants`, `sessions`, `approvals`, `usage_events` (партиционирование по месяцу), `shares`, `audit_events`.
- Шифруемые поля: `preview_enc`, `name_enc` (опционально), `workspace_enc`; ключи — см. §5.
- Ретенция: usage — 90 дней по умолчанию (настраивается), audit — 1 год, sessions — 30 дней. Удаление аккаунта — каскадное, с «tombstone» для аудита.

## 5. Криптографическая модель (фича 13)

### 5.1. Модель угроз

**Противник:** недобросовестный оператор self-host моста. У него root на сервере, доступ к БД, бэкапам, диску, RAM, логам и сетевому трафику; он может менять код моста, подделывать ответы и удалять записи. Он **не** ломает криптографию, не контролирует устройство пользователя и не контролирует edge (вендора).

| Актив | Сегодня видит мост | Цель v2 |
| :--- | :--- | :--- |
| Содержимое файлов и шаров | да (открытым текстом) | нет: E2E-ключи у устройства/браузера |
| Текст команд и вывод инструментов | да | в `blind` — нет; в `terminating` — да, но без записи на диск |
| Имена файлов, заметки, превью approvals | да | нет: шифруются |
| Учётные данные (токены, ключи) | хеши/шифротекст | нет: ключи только у устройства и edge |
| Метаданные (кто, когда, сколько) | да | минимизированы, но не равны нулю |
| Данные других тенантов | при ошибке изоляции — да | нет: per-tenant ключи и изоляция |
| Аудит | может удалить | tamper-evident: хеш-цепочка + Merkle + чекпоинты устройств |

**Границы, которые нельзя обещать:**
- облачный LLM (Gemini/Claude/GPT) видит аргументы и результаты — иначе он не сможет работать; это доверенная сторона, как и сегодня;
- в `terminating`-режиме мост видит live-трафик по определению;
- метаданные соединений (время, объём, частота) видны всегда;
- скомпрометированное устройство или украденный recovery-код не защищаются криптографией.

### 5.2. Три режима доверия

| Режим | Где MCP-сервер | Что видит self-host оператор | Когда использовать |
| :--- | :--- | :--- | :--- |
| **A. Blind relay** (рекомендуется) | На устройстве (`core/server.py`) | Только шифротекст (Noise edge↔device) и метаданные | Self-host с edge; мобильные и корпоративные клиенты |
| **B. Terminating bridge** | На мосту (`bridge/`) | Live-вызовы открытым текстом; at-rest — шифротекст | Self-host без edge, air-gapped, свой домен |
| **C. Local-first** | На устройстве, клиент рядом (Claude Code/Desktop) | Ничего, моста нет | Разработка, максимальная приватность |

**A — как это работает.** Облачный клиент идёт на `https://<edge>/d/<id>/mcp`; edge терминирует TLS (публичный сертификат), устанавливает с устройством Noise IK-сессию (статический ключ устройства запинен в аккаунте) и передаёт кадры через мост. Мост — L4-релей: он видит `tenant_id`, `device_id`, размеры и тайминг, но не JSON-RPC. Даже если оператор подменит мост, он не получит ключ устройства; подмена обнаруживается по пиннингу и аудиту.

**B — что делаем, если edge нет.** Мост сам терминирует MCP. Тогда:
- все данные at-rest (файлы, шары, approvals, имена) шифруются ключами тенантов, которых у моста нет;
- live-трафик не логируется, буферы в памяти, `no_new_privs`, read-only rootfs, egress-фильтр;
- оператор проходит «прозрачность»: публикует версию сборки, digest, SBOM; устройство может запросить `/attest`;
- в UI и документации прямо написано: «оператор этого моста видит ваши команды в момент выполнения; используйте blind-режим, если это неприемлемо».

### 5.3. Ключевая иерархия

```
URK (User Root Key, 32 B, random, создаётся на первом устройстве)
 ├─ HKDF("rhm/v2/tenant-kek")        → KEK тенанта
 │    └─ AEAD(KEK, DEK, aad=object_id) → wrapped DEK для каждого объекта
 │         └─ AES-256-GCM(DEK, данные) → файл / превью / имя / заметка
 ├─ HKDF("rhm/v2/search")            → K_search (blind index, только клиенты)
 ├─ HKDF("rhm/v2/approval")          → K_approval (превью approvals)
 └─ HKDF("rhm/v2/audit")             → K_audit (подпись чекпоинтов)

URK хранится:
 1) sealed box (X25519) на каждое устройство тенанта;
 2) recovery: AEAD(Argon2id(passphrase, 12 слов), URK) — «recovery kit»;
 3) org-режим: Shamir 3-of-5 между админами (опционально).
```

Правила:

- **URK никогда не покидает устройства в открытом виде.** Мост получает только `wrapped_dek` и шифротекст.
- **Новое устройство** получает URK от существующего: QR/короткий код + подтверждение на обоих устройствах (SAS-сравнение). Восстановление — только recovery-кодом.
- **Отзыв устройства**: URK перевыпускается (rotate), новый URK заворачивается на оставшиеся устройства; все DEK перешифровываются лениво (при следующем обращении) или фоновым rewrap-джобом.
- **Ротация**: KEK — по событию (компрометация/увольнение), DEK — по TTL (90 дней) или вручную; версия ключа в AAD, чтобы нельзя было подменить.
- **Алгоритмы**: X25519, Ed25519, HKDF-SHA256, AES-256-GCM (или XChaCha20-Poly1305), Argon2id (64 MiB, 3 итерации). Библиотеки: libsodium (PyNaCl) на устройстве и мосту, WebCrypto в браузере, `libsodium-wrappers` в web-приложении.
- **Формат конверта** (версионируется):

```json
{
  "v": 2,
  "alg": "xchacha20poly1305",
  "kid": "tenant/<id>/kek/3",
  "nonce": "base64url",
  "aad": "object/<type>/<uuid>",
  "wrapped_dek": "base64url",
  "ciphertext_sha256": "hex"
}
```

### 5.4. Что именно шифруется

| Объект | Ключ | Кто расшифровывает | Примечание |
| :--- | :--- | :--- | :--- |
| Файл в шаре | DEK + share key в `#fragment` | Браузер получателя | Сервер не видит ключ; expiry и лимит скачиваний — на мосту |
| Файл в кабинете (upload/download) | DEK, обёрнутый на устройства тенанта | Устройство пользователя | Веб-клиент получает wrapped DEK после OAuth |
| Превью approval (текст команды) | K_approval | Устройство; телефон — sealed box | В БД только шифротекст |
| Имя устройства/агента | KEK тенанта | Кабинет после логина | В мосте — только UUID |
| Рабочая папка агента | KEK тенанта | Устройство/кабинет | Мост видит только флаг «задана» |
| Лог использования | счётчики без payload | — | В БД только tool/status/duration/bytes |
| Аудит | подпись Ed25519 + цепочка | Любой клиент тенанта | Мост не может незаметно переписать |
| Wi-Fi-профили LiveUSB | passphrase пользователя (LUKS) | LiveUSB после ввода | По умолчанию не хранятся |

### 5.5. Метаданные и blind index

- В мосте — только `tenant_id`, `device_id` (UUIDv7), `blob_id`, размерные бакеты (4 КБ / 64 КБ / 1 МБ), округлённое до 5 минут время.
- Имена и пути не индексируются на мосте. Поиск в кабинете — клиентский: кабинет получает список объектов и расшифровывает имена, либо использует blind index `HMAC(K_search, lowercase(name))`; сервер сравнивает только хеши.
- IP-адреса: хеш с солью, ротация соли раз в сутки, хранение 24 часа; в аудит — только страна/ASN, если включено.
- Счётчики использования агрегируются по часам; события старше 90 дней сворачиваются в суточные суммы.

### 5.6. Подмена, аудит и аттестация

- **Хеш-цепочка**: каждое событие аудита содержит `prev_hash`; раз в час мост публикует подписанный Merkle root. Устройство хранит последний известный root; при расхождении показывает предупреждение «мост переписал историю».
- **Чекпоинты**: устройство раз в сутки подписывает `(root, seq)` своим ключом и отправляет в аккаунт; кабинет сверяет.
- **Сборки**: воспроизводимая сборка, `cosign`-подпись образов, SBOM, публикация digest. `rhm-bridge verify` запрашивает у моста `/attest` (подписанный digest работающего образа) и сверяет с релизом.
- **Appliance-опция**: TPM 2.0 quote для корпоративных инсталляций; без TPM — TOFU + прозрачный лог версий.
- **Пентест** перед GA: отдельный этап, включая попытку оператора прочитать данные клиента в blind-режиме.

### 5.7. Чеклист «недобросовестный хостер»

| # | Проверка | Ожидание |
| :--- | :--- | :--- |
| 1 | Дамп БД моста | Нет plaintext файлов, имён, команд, превью |
| 2 | Дамп диска/бэкапа | Только шифротекст и метаданные |
| 3 | Перехват трафика в blind | Только Noise-кадры |
| 4 | Подмена моста | Пиннинг ключа устройства ломает сессию, аудит фиксирует |
| 5 | Чужой тенант | Нет доступа: ключи разные, запросы скоупятся |
| 6 | Удаление аудита | Merkle root и чекпоинты обнаруживают |
| 7 | Кража OAuth-токена | Короткий TTL, привязка к agent/device, отзыв |
| 8 | Подделка устройства | Ключ на устройстве, подпись hello, cert pinning |
| 9 | Метаданные | Минимизированы; явно описано, что видно |
| 10 | Terminating-режим | Явное предупреждение + отказ от логов + аттестация |

### E2. Hover-панель активности и прерывание (фича 2)

**Цель.** При наведении на пульсирующую иконку видеть, что именно выполняется, какой текст запроса, сколько длится, и уметь прервать — не открывая кабинет.

**UX.**
- Панель 420×до 320 px, появляется над иконкой, не крадёт фокус, закрывается при уходе курсора (задержка 300 мс).
- Список активных вызовов: `агент · инструмент · превью · таймер · [Прервать]`.
- Для `bash_exec`/`run_job` — команда; для `device_control` — действие и текст диалога; для `write_file` — путь; для `share_file` — имя.
- Кнопки: **Прервать вызов**, **Отключить агента** (разрывает сессию, не трогая туннель), **Открыть журнал**.
- Переключатель «Показывать полный текст» (по умолчанию превью 160 символов, секреты вырезаны).
- Если вызов ждёт approval — панель показывает причину и кнопки «Разрешить/Запретить».

**Изменения.**
- `core/activity.py`: модель `ActiveCall {id, agent, tool, preview, started_at, status, bytes, cancellable}`.
- `core/mcp_tools.py`: `abort_event` на вызов; `_run_bash` и джобы проверяют его; `job_kill` переиспользуется.
- `core/agent.py`: отмена по `call_id`; ответ клиенту `-32800 cancelled` (JSON-RPC) с человекочитаемым текстом.
- `desktop/RhmTray`: Flyout-окно, таймеры, кнопки, доступность (клавиатура, screen reader).
- Редактирование: `core/redact.py` (токены, пароли, ключи, `Authorization`, `--password`), плюс ограничение частоты событий (не более 10/с).

**Шаги.**
1. Схема событий и буфер; тесты редактирования.
2. Abort-механика для `bash_exec`, `run_job`, `job_kill`; тест «убить дерево процессов».
3. Abort для approval (закрыть запрос как `cancelled`).
4. Flyout и таймеры; обработка нескольких параллельных вызовов.
5. «Отключить агента»: закрыть сессию, отозвать токен сессии, узел продолжает работать.
6. E2E: длинная команда, несколько вызовов, отключение.

**Критерии.**
- Прерывание останавливает процесс (и дерево) за < 2 с, клиент получает структурированную ошибку.
- В превью никогда не попадают секреты (тест с `--password`, `Authorization: Bearer`).
- Панель не мешает работе: не перехватывает клики вне себя, не появляется при `paused`.

**Оценка:** 12 pd. **Зависимости:** E1. **Риски:** обрыв вызова на стороне клиента (Gemini может не показывать ошибку) — документировать поведение.

### E3. Режим агента: Read-only / Agent (фича 3)

**Цель.** У каждого подключённого агента — свой режим, переключаемый правой кнопкой в трее и в кабинете; read-only соблюдается на всех трёх уровнях.

**UX.**
- В ПКМ-меню — радио «Read-only / Agent» для выбранного агента (если агентов несколько — подменю со списком).
- Переключение в `Agent` требует подтверждения: «Claude получит право выполнять команды и менять файлы. Продолжить?».
- В кабинете — та же настройка в карточке агента, с журналом изменений.
- Новый агент по умолчанию `read_only`; повышение — только явным действием.
- В `tools/list` read-only агент видит только разрешённые инструменты; попытка мутации возвращает `mode_denied` с подсказкой.

**Изменения.**

| Слой | Работа |
| :--- | :--- |
| `core/mcp_tools.py` | `SessionContext(mode, workspace, scopes, agent_label)`; замена глобального `_READ_ONLY` на контекст; `configure_session()`; все проверки — через контекст |
| `core/agent.py` | Приём `session_start` из туннеля v2; контекст на вызов; запрет смешивания контекстов |
| `bridge/policy.py` | Фильтрация `tools/list` по scope/mode; отказ `tools/call`; аудит |
| `bridge/api/agents.py` | `PATCH /v1/agents/{id}` `{mode}`; проверка владельца тенанта |
| Трей | Пункт меню, подтверждение, отображение текущего режима |
| Кабинет | Переключатель + история |

**Модель прав.**

| Инструмент | `read_only` | `agent` |
| :--- | :---: | :---: |
| `system_info`, `system_vitals`, `mesh_status` | ✅ | ✅ |
| `list_dir`, `read_file`, `grep_search`, `glob_find` | ✅ | ✅ |
| `share_list` | ✅ | ✅ |
| `write_file`, `edit_file` | ❌ | ✅ (в пределах write roots) |
| `bash_exec`, `run_job`, `job_kill` | ❌ | ✅ (политика подтверждений) |
| `share_file`, `serve_dir`, `unshare` | ❌ | ✅ |
| `device_info` | ✅ | ✅ |
| `device_control`, `device_capture`, `device_messages` | ❌ | ✅ (по переключателям узла) |
| `mesh_update` | ❌ | ✅ + подтверждение |

**Шаги.**
1. Рефактор `mcp_tools` на контекст; зелёные существующие тесты (1258) — обязательное условие.
2. `bridge/policy.py`: scope/mode → allowlist инструментов; тесты на каждый инструмент.
3. Туннель v2: `hello` с `mode`, `workspace`, `agent_id`; обратная совместимость со старым `hello`.
4. Трей: переключение, подтверждение, синхронизация с мостом.
5. Кабинет: PATCH, история, отзыв.
6. Понижение режима: остановка мутирующих джобов, аудит.

**Тесты.** Матрица «инструмент × режим × слой» (мост отдельно, узел отдельно, вместе); попытка обойти мост прямым вызовом узла; старый узел без контекста (должен работать в глобальном режиме).

**Критерии.**
- Read-only агент не может выполнить ни один мутирующий инструмент ни через мост, ни через прямой вызов.
- Переключение применяется к новым вызовам < 1 с; активные — по настройке.
- В аудите видно, кто и когда менял режим.

**Оценка:** 14 pd. **Зависимости:** F1 (контекст), E1. **Риски:** рефактор глобального состояния может затронуть device-ветку и Termux — покрыть тестами.

### E4. Кабинет аккаунта: устройства и агенты (фича 4)

**Цель.** Одно место, где видно все устройства с MCP, всех агентов, которые ими управляют, их статистику и права; можно переименовать, отключить, выполнить команду, поделиться файлом и настроить доступ.

**Информационная архитектура.**

```
/                         Обзор: устройства онлайн/офлайн, алерты, последние сессии
/devices                  Список устройств (таблица, фильтры, поиск)
/devices/{id}             Карточка: статус, версия, агенты, сессии, статистика,
                          файлы, команды, права, опасная зона
/agents                   Список агентов: клиент, устройство, режим, scopes,
                          последняя активность, отозвать
/usage                    Статистика: вызовы, топ инструментов, ошибки, объём
/shares                   Шары: срок, скачивания, отозвать
/settings                 Аккаунт, тенанты, безопасность, ретенция, уведомления
```

**Карточка устройства.**
- Заголовок: имя (редактируемое), ОС/арх, версия узла, статус, последний контакт, режим по умолчанию.
- Кнопки: **Переименовать**, **Переподключить**, **Проверить связь**, **Обновить узел**, **Отозвать**.
- «Агенты»: список с режимом и последней активностью; кнопка «Отозвать доступ».
- «Команды»: форма `command`, `timeout`, `run_as_job`; выполнение требует подтверждения на устройстве (настройка), вывод — по мере готовности; аудит.
- «Файлы»: дерево рабочей папки (read-only по умолчанию), скачать/загрузить, «Поделиться» (срок, пароль, лимит скачиваний).

### E5. Рабочая директория агента (фича 5)

**Цель.** Для каждого агента — своя рабочая папка; относительные пути и `bash_exec` работают в ней, выход за пределы запрещён.

**UX.**
- Трей: «Рабочая папка…» → нативный диалог; показывает текущую, кнопка «Сбросить».
- Кабинет: поле пути + «Выбрать» (для онлайн-устройства — browsable дерево).
- В hover-панели и журнале видно, в какой папке выполняется вызов.
- Если папка исчезла/недоступна — узел отвечает `workspace_unavailable`, предлагает выбрать другую; не падает.

**Правила.**
- Путь должен быть абсолютным, существовать, быть каталогом, резолвиться без symlink-прыжков за пределы allowlist.
- Allowlist: `MESH_WRITE_ROOTS` (существующий) + выбранная папка; запись — только в неё.
- Windows: нормализация `\`, junction/reparse points, длинные пути (`\\?\`), диск-relative пути запрещены.
- Смена папки не меняет уже запущенные джобы; новые вызовы — в новой.
- Для Android/Termux — `~/storage/shared/...` с проверкой прав.

**Изменения.**
- `SessionContext.workspace`; `_resolve()` и `_run_bash(cwd=...)`; `list_dir`/`glob`/`grep` — от неё.
- `bridge/api/agents.py`: `PATCH {workspace}` (валидация на устройстве, не на мосте).
- Трей/кабинет: выбор и отображение.
- Аудит: кто и когда менял папку.

**Шаги.** Контекст → валидация → cwd в командах → UI → тесты (symlink, junction, кириллица, пробелы, UNC, удалённая папка).

**Критерии.**
- Относительный путь в `read_file`/`write_file` резолвится от рабочей папки.
- Попытка выйти за пределы (`..`, symlink, junction) отклоняется.
- Смена папки в трее применяется к следующему вызову.

**Оценка:** 7 pd. **Зависимости:** E3. **Риски:** Windows-пути и Termux — разные кодовые ветки, покрыть матрицей.

### E6. LiveUSB-агент (фича 6)

**Цель.** Загрузочная флешка, которая на чужой машине поднимает узел, сама находит/подгружает сетевой драйвер, подключается к известным Wi-Fi и позволяет подключить устройство к аккаунту с телефона.

**Состав поставки.**
1. `rhm-live-<version>.iso` (UEFI + Legacy, Secure Boot через подписанный shim Ubuntu).
2. `rhm-usb-writer` — запись образа с проверкой (в трее и CLI; Windows — raw write с подтверждением, macOS — `diskutil`, Linux — `dd`); совместимость с Ventoy.
3. `rhm-live-wizard` — мастер на экране загрузки.
4. `rhm-live-tui` — резервный консольный режим для headless.

**База.** Ubuntu 24.04 LTS live (подписанный shim, широкий `linux-firmware`), overlay с:
`network-manager`, `wpa_supplicant`, `iw`, `rfkill`, `usb-modeswitch`, `modemmanager`, `qrencode`, `avahi`, `python3-gi`, `rhm-node`, `rhm-live-wizard`.
Пакеты драйверов: `linux-firmware`, `firmware-iwlwifi`, `firmware-realtek`, `firmware-brcm80211`, `broadcom-sta-dkms`, `rtl8812au-dkms`, `rtl8821ce-dkms`, `rtl88x2bu-dkms`, `mt76`-прошивки — в офлайн-пул `/opt/rhm/drivers`.
Ethernet/LAN: `e1000e`, `igb`, `ixgbe`, `r8169`, `alx`, `tg3`, `atlantic`, `usbnet`/`cdc_ether`, `rndis_host` — в базовом ядре и firmware-пуле, чтобы «проводной» сценарий работал без загрузки драйверов.

**Автоподключение к известным Wi-Fi.** При создании флешки пользователь может положить профили (SSID, security, пароль) в LUKS-контейнер `rhm-wifi`; мастер при загрузке формирует `NetworkManager`-профили (`nmcli connection add ...`) с приоритетом, скрытыми SSID и WPA2/WPA3, раскладывает их в `/etc/NetworkManager/system-connections/` (0600) и запускает `nmcli connection up` в порядке приоритета. Если контейнера нет — только ручной выбор сети. Пароли не попадают в открытый `/boot` и в логи.

**Логика драйверов (при загрузке, до мастера).**

```
rhm-hwprobe:
  1. Перечислить NIC: lspci -nnk, lsusb, /sys/class/net/*/device/driver
  2. Для каждого без драйвера — сопоставить с manifest.json (PCI/USB ID → модуль/пакет)
  3. modprobe кандидатов; если модуля нет — dkms autoinstall из /opt/rhm/drivers
  4. Если драйвер не найден:
       a. есть USB-тетеринг телефона → скачать пакет с зеркала (подпись проверяется)
       b. нет сети → показать на экране точный ID устройства и ссылку на пакет
  5. Записать отчёт в /var/log/rhm/live.log и на экран (статус-строка)
```

**Логика сети.**
1. Попробовать известные сети (профили из зашифрованного контейнера, если пользователь их положил; порядок по приоритету).
2. Если нет — экран выбора Wi-Fi: SSID, сигнал, безопасность; ввод пароля; WPA2/WPA3; скрытая сеть; 802.1X — во второй версии.
3. Проверка интернета + captive portal; если портал — открыть браузер.
4. Ethernet — автоматически, если воткнут.
5. Нет сети вообще — инструкция «раздайте интернет с телефона по USB» + повторное сканирование.

**Персистентность.**
- По умолчанию — RAM, ничего не пишется на диск.
- Опционально — LUKS-раздел `rhm-persist` (пароль при создании флешки), хранит `agent.env` и ключи.
- «Установить на диск» — отдельный пункт, с предупреждением о стирании.

**Безопасность.**
- На флешке нет секретов по умолчанию; ключи генерируются при загрузке.
- Wi-Fi-профили — только в LUKS-контейнере с паролем пользователя.
- Secure Boot: подписанный shim; DKMS-модули требуют MOK-энроллмента — мастер объясняет и предлагает либо энролл, либо отключение Secure Boot.
- Автообновление LiveUSB-образа — вручную (перезапись), версия видна на экране.

**Сборка.**
- `liveusb/build.sh --base ubuntu-24.04 --version <v> --drivers all|minimal --out dist/`.
- Воспроизводимость: фиксированные версии пакетов, `sha256` манифест, подпись `minisign`/`cosign`, SBOM.
- CI: еженедельная сборка + ночная проверка загрузки в QEMU (UEFI/BIOS, Secure Boot on/off, виртуальные NIC).

**Шаги.**
1. Каркас `liveusb/` (chroot/overlay, systemd-юниты, брендинг).
2. `rhm-hwprobe` + manifest + DKMS-пул.
3. Мастер Wi-Fi + проверка связи.
4. QR и передача сессии (E6.1).
5. Интеграция `rhm-node`, автозапуск, логи.
6. Writer (CLI + GUI) и проверка записи.
7. Матрица железа: Intel AX201, Realtek RTL8852, Broadcom BCM4360, USB RTL8812AU, Ethernet-only, без NIC.
8. Документация и recovery (что делать, если не загрузилось).

**Критерии.**
- На 5 из 5 тестовых машин (UEFI, Secure Boot on/off) система загружается и поднимает узел.
- Машина без драйвера Wi-Fi получает его из офлайн-пула или через USB-тетеринг.
- Известная Wi-Fi подключается автоматически; незнакомая — через мастер.
- Образ подписан, sha256 совпадает, запись проверяется побайтово.

**Оценка:** 45 pd. **Зависимости:** E7/E6.1, E8, `core/agent.py`. **Риски:** покрытие драйверов (высокое), размер образа (~2 ГБ), Secure Boot и DKMS, legal (прошивки/лицензии).

### E6.1. Wi-Fi-мастер, QR и продолжение с телефона (фича 6.1)

**Цель.** При старте без интернета сразу предложить Wi-Fi; после подключения — QR, по которому телефон продолжает онбординг.

**Поток.**

```
Загрузка → hwprobe → [нет сети] → экран Wi-Fi → выбор SSID → пароль →
подключение → проверка интернета → [QR: https://<edge>/live/<code>] →
телефон: Google-вход → устройство найдено → выбор агента → добавление MCP →
авторизация → узел подключён к аккаунту → на экране «Готово»
```

- QR содержит `https://<edge>/live/<code>` и **отпечаток ключа** (короткий SAS), код одноразовый, TTL 15 минут.
- На экране — крупный QR, код, статус («ожидание телефона»), кнопка «Продолжить на этом ПК» (открывает браузер).
- Телефон после сканирования видит: имя устройства, ОС, «Подключить», выбор агента, инструкцию, кнопку «Авторизовать».
- После подтверждения на телефоне узел получает grant, подключается к мосту, экран меняет статус на «Готово» и показывает, какой агент подключён.
- Если телефон не подходит (нет камеры/клиента) — «Продолжить на ПК»: локальный браузер на `http://localhost:8080/start`, тот же поток.

**Изменения.**
- `liveusb/wizard/` — GTK4 (PyGObject) + `qrencode`/Pillow.
- `edge/api/live.py` — создание live-сессии, привязка кода к устройству, статус, завершение.
- `core/agent.py` — режим `live` (получить grant, подключиться, не хранить секреты после выключения).
- `web/live/` — мобильная страница онбординга (адаптив, ru/en).
- TUI-версия для headless: QR в терминале (ANSI/Unicode), тот же код.

**Тесты.** Одноразовость кода, TTL, повторное сканирование, обрыв на середине, два телефона одновременно, отсутствие интернета после подключения к Wi-Fi, captive portal.

**Критерии.**
- От загрузки до QR — < 60 с на тестовой машине.
- Мобильный сценарий проходится без терминала.
- Код перестаёт работать после использования и по TTL.

**Оценка:** 14 pd. **Зависимости:** E6, E7, E8. **Риски:** мобильные браузеры и Google OAuth в WebView; каптивный портал; отсутствие камеры.

### E7. Выбор облачного агента и инструкция по добавлению MCP (фича 7)

**Цель.** После установки пользователь выбирает Gemini / Claude / GPT (или «другой клиент») и получает страницу с уже скопированным адресом MCP и точной инструкцией; адрес копируется автоматически.

**Точки входа.**
- Финал установщика (Windows GUI, `install.sh`, LiveUSB): кнопка **«Подключить агента»**.
- Трей: «Открыть кабинет → Подключить агента».
- Кабинет: карточка устройства → «Добавить агента».
- Прямая ссылка `https://<edge>/start?device=<id>&code=<pairing>` (код одноразовый).

**Экран выбора.**

| Карточка | Что показываем |
| :--- | :--- |
| **Gemini** (Web/App) | Settings → Connectors → Add MCP server → вставить URL; предупреждение, что ссылка = пароль |
| **Claude** (Web/Desktop) | Settings → Connectors → Add custom connector → URL; кнопка «Авторизовать» (OAuth) |
| **ChatGPT** | Settings → Connectors → Advanced → Add MCP; URL; OAuth или токен |
| **Claude Code / Cursor / другой** | Готовый JSON-сниппет и команда `claude mcp add --transport http rhm <url>` |

**Поведение.**
- URL формируется из edge-алиаса (`/d/<device>/mcp`) и сразу копируется в буфер; кнопка «Скопировать ещё раз».
- Рядом — QR для мобильного клиента и кнопка «Проверить подключение»: страница слушает событие `initialize` от клиента и показывает «Готово» с именем агента; таймаут 2 минуты → блок «Что делать, если не подключается» (DNS, сертификат, ссылка устарела, нужен OAuth).
- Для клиентов с OAuth — кнопка «Авторизовать» ведёт в E8; для остальных создаётся `AgentConnection` с меткой клиента при первом вызове.
- Предупреждение о безопасности: «Любой, у кого есть эта ссылка, управляет устройством. Перевыпустить» — кнопка ротации link key.
- Языки ru/en; скриншоты/гифки для каждого клиента; версия инструкции хранится вместе с релизом (клиенты меняют UI).

**Изменения.**
- `web/start/` — страница выбора и инструкций (адаптив).
- `edge/api/onboarding.py` — сессии онбординга, ожидание `initialize`, статус.
- `bridge/api/agents.py` — создание агента при первом вызове по link key.
- Установщики — deep-link на `/start` с кодом; трей — пункт меню.
- Контент инструкций — в `docs/clients/*.md`, рендер на странице.

**Шаги.**
1. Схема onboarding-сессии и API.
2. Страница выбора + копирование + QR.
3. Инструкции для 4 клиентов, i18n.
4. «Проверить подключение» через событие `initialize`.
5. Deep-link из установщиков и трея.
6. A/B-проверка с новым пользователем (юзабилити-тест на 5 людях).

**Критерии.**
- Новый пользователь проходит путь «установка → первый инструмент» < 5 минут без чтения README.
- Адрес копируется автоматически и совпадает с тем, что видит узел.
- «Проверить подключение» показывает успех в течение 10 с после первого `initialize`.

**Оценка:** 18 pd. **Зависимости:** E8, E4, установщики. **Риски:** UI облачных клиентов меняется — контент должен версионироваться и обновляться без релиза кода (CMS/JSON).

### E8. Авторизация и выдача доступа агенту (фича 8)

**Цель.** После добавления MCP пользователь проходит авторизацию (Google), подтверждает доступ на устройстве, и агент получает токен, привязанный к устройству, режиму и scopes.

**Потоки.**

**8.1. OAuth-клиент (Claude, ChatGPT, Cursor).**
1. Клиент без токена → `401` + `WWW-Authenticate: Bearer resource_metadata="…"`.
2. Клиент читает метаданные, регистрируется через DCR (allowlist).
3. Открывает `/authorize` → Google OIDC → consent: какое устройство, какой режим, какие scopes, имя агента.
4. Редирект с `code` → клиент меняет на `access_token` + `refresh_token` (PKCE).
5. Первый вызов: устройство показывает approval «Claude подключается, отпечаток …» → пользователь разрешает.
6. Токен живёт 15 минут, refresh — 30 дней; отзыв в кабинете/трее — мгновенный.

**8.2. Link-key клиент (Gemini сегодня).**
1. Пользователь вставляет URL с `lk_…`.
2. Узел/мост создаёт `AgentConnection` с `label` из `clientInfo.name` и режимом по умолчанию `read_only`.
3. Approval на устройстве при первом подключении.
4. Ротация link key в кабинете отзывает именно этого агента (и создаёт новый ключ, если нужно).

**8.3. Self-host мост.**
- Доверяет токенам edge (JWKS) либо запускает собственный AS с Google-брокером (см. E11).
- В offлайн/air-gapped — локальный AS с recovery-ключом администратора; OAuth-клиенты подключаются к нему напрямую.

**Consent-экран (обязательные элементы).**
- Кто просит доступ (имя клиента, иконка, redirect URI).
- Какое устройство (имя, ОС, последние 4 символа отпечатка).
- Режим: Read-only / Agent (по умолчанию Read-only).
- Scopes человеческим языком: «читать файлы», «выполнять команды», «управлять телефоном», «публиковать файлы».
- Срок: «пока не отзовёте» / «30 дней».
- Кнопки: «Разрешить», «Отказать», «Подробнее».

**Approval на устройстве.**
- Уведомление + hover-панель: «Claude (новый) просит доступ. Отпечаток ключа: AB12-CD34. Режим: Read-only».
- «Разрешить один раз» / «Разрешить всегда для этого агента» / «Запретить».
- Таймаут 90 с → отказ; повторный запрос — не раньше чем через 30 с (анти-спам).
- Для знакомого агента с тем же ключом — без запроса (политика настраивается).

**Токен (claims).**

```json
{
  "iss": "https://edge.example",
  "sub": "account/<id>",
  "aud": "device/<device_id>",
  "tenant": "<tenant_id>",
  "device": "<device_id>",
  "agent": "<agent_connection_id>",
  "mode": "read_only",
  "scopes": ["device:read"],
  "jti": "<uuid>",
  "iat": 1760000000,
  "exp": 1760000900
}
```

**Изменения.**
- `edge/auth/oauth.py` — AS: metadata, DCR, authorize, token, revoke, JWKS.
- `edge/auth/google.py` — OIDC, state/nonce, PKCE.
- `edge/auth/consent.py` — consent-сессия, привязка к устройству.
- `bridge/auth.py` — проверка JWT (JWKS, кэш), `jti`-denylist, привязка к агенту.
- `core/agent.py` — approval-запросы, кэш «разрешено всегда» (по отпечатку ключа агента).
- `web/consent/` — страница согласия.
- Кабинет — список агентов и отзыв.

**Тесты.**
- OAuth conformance (PKCE обязателен, `redirect_uri` точный, `state` одноразовый, replay кода).
- Просроченный/поддельный/чужой токен → 401, без утечки деталей.
- Отзыв агента → следующий вызов 401 < 5 с.
- Approval: таймаут, «всегда», отзыв «всегда», параллельные запросы.
- CSRF на consent, кликджекинг (X-Frame-Options), open redirect.

**Критерии.**
- Claude/ChatGPT подключаются по OAuth без ручного копирования токена.
- Gemini работает по link key без регрессий.
- Ни один токен не даёт доступ к другому устройству/тенанту.
- Все выдачи и отзывы — в аудите.

**Оценка:** 25 pd. **Зависимости:** F2, E4, E7. **Риски:** DCR-политика и поддержка клиентов; Google OAuth для self-host доменов (см. E11).

### E9. Установка в Docker (фича 9)

**Цель.** `docker compose up -d` поднимает узел или мост без ручной настройки, с разумной изоляцией и честно описанными ограничениями.

**Образы.**

| Образ | Назначение | База |
| :--- | :--- | :--- |
| `ghcr.io/<org>/rhm-node` | Узел (agent + mcp_tools + server) | `python:3.12-slim`, multi-arch amd64/arm64 |
| `ghcr.io/<org>/rhm-bridge` | Мост (gateway v2) | `python:3.12-slim` + `uvicorn` |
| `ghcr.io/<org>/rhm-web` | Кабинет | `nginx:alpine` + static |
| `ghcr.io/<org>/rhm-allinone` | Мост + кабинет + SQLite для быстрого старта | один контейнер |

**Compose-профили.**
- `node` — узел, монтирует `/workspace` (рабочая папка) и `/data` (конфиг/ключи).
- `bridge` — мост + Postgres + Caddy (ACME или internal CA).
- `dev` — всё вместе на localhost.

**Безопасность контейнера узла.**
```yaml
user: "10001:10001"
read_only: true
cap_drop: [ALL]
security_opt: ["no-new-privileges:true"]
tmpfs: ["/tmp:rw,noexec,nosuid,size=64m"]
volumes:
  - rhm-data:/data
  - ${WORKSPACE:-./workspace}:/workspace
```
- **Не монтируем** `docker.sock`, не даём `privileged`.
- Для полного контроля над хостом — только явные монтирования; в документации таблица «что работает в контейнере, что нет».
- `device_control`/`device_capture` — только при `--device` и udev; по умолчанию выключены.
- Сетевой режим: bridge (по умолчанию) или `network_mode: host` для LAN-обнаружения (опция).

**Ограничения (публикуем честно).**

| Сценарий | В контейнере |
| :--- | :--- |
| Файлы в `/workspace` | ✅ |
| Команды в контейнере (не на хосте) | ✅ |
| Управление хостом (реестр, службы, GUI) | ❌ (нужен агент на хосте) |
| Телефон/Termux | ❌ |
| Автообновление узла | ⚠️ только перезапуском контейнера |
| Живой трей | ❌ (UI на хосте) |

**Мост в Docker.** Postgres 16, том `pgdata`, Caddy с `tls internal` для self-host или ACME для домена; healthcheck `/health`; миграции при старте; backup-скрипт `docker compose exec bridge rhm backup`.

**CI.** `buildx` под amd64/arm64, `cosign sign`, SBOM (`syft`), триггер по тегу; проверка `docker run --rm image rhm-node --version`.

**Шаги.** Dockerfile узла → entrypoint (инициализация конфига, права) → compose → мост → CI/подпись → документация и примеры → тест на чистой машине.

**Критерии.**
- `docker compose -f compose.node.yml up -d` на чистой машине даёт рабочий узел за < 2 минуты.
- Контейнер не пишет в rootfs, не имеет лишних capabilities.
- Документация явно перечисляет ограничения.

**Оценка:** 12 pd. **Зависимости:** F1. **Риски:** ожидания «контейнер управляет хостом»; размер образа; обновления.

### E10. Лёгкая установка self-host и самописный сертификат (фича 10)

**Цель.** Один скрипт: поставить мост на это устройство или по SSH, автоматически настроить TLS (включая собственный CA), проверить и выдать готовый админ-доступ.

**Интерфейс.**

```bash
# локально
curl -fsSL https://<edge>/install-bridge.sh | bash -s -- --domain=rhm.example.com --email=me@example.com

# по SSH
./install-bridge.sh --ssh=root@203.0.113.10 --domain=rhm.example.com --email=me@example.com

# docker
./install-bridge.sh --docker --domain=rhm.example.com --email=me@example.com

# без домена, свой CA
./install-bridge.sh --self-signed --host=192.168.1.10

# предпросмотр / удаление / бэкап
./install-bridge.sh --dry-run
./install-bridge.sh --uninstall --keep-data
./install-bridge.sh --backup /root/rhm-backup.tar.gz
```

**Флаги:** `--domain`, `--host`, `--email`, `--ssh`, `--identity`, `--docker`, `--self-signed`, `--acme`, `--edge-tunnel`, `--port`, `--no-postgres`, `--data-dir`, `--dry-run`, `--uninstall`, `--backup`, `--restore`, `--yes`, `--lang`.

**Шаги установки.**
1. Preflight: ОС, arch, RAM/диск, порты 80/443, DNS, наличие Docker/Python, часовой пояс.
2. Пользователь `rhm`, каталоги `/etc/rhm`, `/var/lib/rhm`, `/var/log/rhm`.
3. Секреты: `admin_token`, `jwt_key`, `db_password`, `bridge_id`; запись в `/etc/rhm/bridge.env` (0600).
4. БД: Postgres (по умолчанию) или SQLite (`--no-postgres`); миграции.
5. TLS:
   - **ACME** — Caddy, HTTP-01/TLS-ALPN, автопродление; требует домен + 80/443.
   - **Self-signed (свой CA)** — генерируем CA + leaf с SAN (`domain`, `host`, `localhost`, IP), Caddy `tls internal`; CA отдаётся по `/ca.crt`; печатаем SHA-256 отпечаток; страница `/trust` с инструкциями для Windows/macOS/Linux/iOS/Android.
   - **Edge tunnel** — исходящий туннель к edge, публичный сертификат на edge, входящие порты не нужны (рекомендуется для домашнего self-host и мобильных клиентов).
6. systemd-юниты `rhm-bridge`, `rhm-worker` (usage/cleanup), `rhm-backup.timer`; `RuntimeDirectory`, `NoNewPrivileges`, `ProtectSystem=strict`.
7. Администратор: логин через Google (E11) или локальный recovery-ключ; вывод recovery kit (тенант, ключ, QR) — **один раз**.
8. Проверка: `/health`, TLS-цепочка, БД, очередь, публичный URL; печать итоговой таблицы.
9. Идемпотентность: повторный запуск обновляет, не ломая данные; `--dry-run` показывает план.

**SSH-режим.**
- Проверка host key, `ssh -o BatchMode=yes`, копирование скрипта, потоковый вывод, код возврата.
- Пароль — только интерактивно, не в аргументах и не в истории.
- Поддержка `--identity`, jump-host (`--proxy-jump`).

**Сертификат: что важно сказать пользователю.**
- Мобильные приложения (Gemini/Claude) **не доверяют** пользовательскому CA → для них нужен публичный сертификат: ACME-домен или edge tunnel.
- Self-signed подходит для браузера/десктопа после установки CA; на Android — ограничения (user CA не для всех приложений).
- Отпечаток CA показываем в кабинете и в QR, чтобы исключить подмену.

**Шаги разработки.**
1. Каркас скрипта, preflight, dry-run, логирование.
2. Локальная установка (Postgres, systemd, миграции).
3. TLS: ACME + internal CA, trust-страница.
4. SSH-ветка и стриминг вывода.
5. Edge tunnel-ветка.
6. Бэкап/восстановление/удаление.
7. Тесты: shellcheck, VM-матрица (Ubuntu 22/24, Debian 12), «грязная» машина, повторный запуск, откат при сбое.

**Критерии.**
- На чистой Ubuntu 24 установка < 5 минут, заканчивается рабочим `/health` и входом в кабинет.
- Self-signed: браузер после установки CA не ругается; отпечаток совпадает.
- Повторный запуск не теряет данные; `--uninstall --keep-data` оставляет БД.
- Все секреты — 0600, не попадают в логи.

**Оценка:** 22 pd. **Зависимости:** F1, E9, E11. **Риски:** разнообразие дистрибутивов; ACME за NAT; доверие к CA на мобильных.

### E11. Google-аккаунт для self-host моста и миграция устройств (фича 11)

**Цель.** Владелец моста подтверждает Google-аккаунт и владение хостом, после чего может перенести на свой мост ранее подключённые устройства, не переустанавливая их.

**Привязка аккаунта.**

- **Вариант A (рекомендуется): вендорный OAuth-брокер.** Google-клиент один, redirect — `https://<edge>/auth/google/callback`. После логина edge выдаёт мосту одноразовый подписанный `link_code` (TTL 5 минут), мост обменивает его на `account_id` + `tenant_id`. Не нужно регистрировать redirect для каждого домена.
- **Вариант B: собственный Google-клиент.** Пользователь создаёт OAuth client в Google Cloud, указывает redirect `<bridge>/auth/google/callback`. Больше контроля, больше шагов; документация и мастер.
- **Вариант C: без Google** — локальный админ с recovery-ключом (для air-gapped).

**Подтверждение владения хостом.**
- Мост показывает код `rhm-verify=<nonce>`.
- Пользователь добавляет DNS TXT `_rhm.<domain>` **или** файл `/.well-known/rhm-bridge-verify.txt`.
- Мост проверяет DNS/HTTP, отправляет proof на edge; edge подписывает binding `{account_id, tenant_id, bridge_id, domain, verified_at}`.
- Повторная привязка домена к другому аккаунту — только после отвязки и периода ожидания (7 дней), чтобы нельзя было угнать домен.

**Миграция устройств.**

```
Account → «Перенести на мой мост» → preflight (мост жив, версия, место) →
edge создаёт migration grants (по одному на устройство, TTL 15 мин) →
каждому узлу: admin-команда switch_bridge {url, grant, edge_url} →
узел подключается к новому мосту, предъявляет grant →
мост валидирует grant у edge → устройство помечается moved →
старый мост отзывает регистрацию через 24 ч (grace) →
link keys перевыпускаются; alias /d/<id> остаётся прежним
```

**Состояния миграции:** `proposed → approved → migrating → done | failed | rolled_back`.
- Прогресс по каждому устройству; ошибки (офлайн, отказ, таймаут) — с действиями «повторить», «пропустить», «откатить».
- Офлайн-устройство получает команду при следующем подключении (очередь, TTL 24 ч).
- Откат в течение 7 дней: обратная команда `switch_bridge` на публичный мост + восстановление регистрации.

**Что меняется у пользователя.**
- При использовании edge-алиаса — **ничего**, MCP-адрес прежний.
- Без алиаса — мастер показывает новый URL и копирует его; старый работает до отзыва.
- В кабинете — баннер «Устройство на вашем мосте» и ссылка на его админку.

**Данные.** `Bridge`, `Migration`, `MigrationItem`, `AccountBinding`; аудит каждого шага; edge хранит только `account_id`, `tenant_id`, `bridge_id`, `domain`, `verified_at`.

**Шаги.**
1. Google OIDC (брокер A) + `link_code` + binding.
2. Ownership proof (DNS TXT + well-known).
3. Модель миграции и API.
4. Команда `switch_bridge` в узле, валидация grant.
5. Очередь для офлайн-устройств, прогресс, откат.
6. Перевыпуск link keys, grace-отзыв.
7. UI кабинета: мастер миграции, статусы, откат.
8. E2E: 3 устройства, одно офлайн, откат.

**Критерии.**
- Пользователь переносит 3 устройства без переустановки и без смены адреса (при alias).
- Откат возвращает всё за < 5 минут.
- Домен нельзя привязать к чужому аккаунту без подтверждения.

**Оценка:** 28 pd. **Зависимости:** E10, E12, E8. **Риски:** Google OAuth-верификация; DNS-пропагация; «застрявшие» офлайн-устройства.

### E12. Fallback при недоступности self-host моста (фича 12)

**Цель.** Если пользовательский мост недоступен, система сама предлагает и выполняет переход на публичный мост или переустановку self-host, не теряя устройство и адрес.

**Классификация сбоев.**

| Симптом | Причина | Действие |
| :--- | :--- | :--- |
| DNS не резолвится | домен/регистратор | fallback + уведомление |
| TLS-ошибка/истёк сертификат | ACME/CA | fallback + ссылка «перевыпустить» |
| 502/503/таймаут | мост лежит/перегружен | fallback |
| 401 на WS | ключи/привязка | не fallback, а диагностика (перепривязка) |
| Диск/БД | инфраструктура | fallback + алерт |

**Политика узла.**
- Конфиг: `MESH_GATEWAY` (primary), `MESH_FALLBACK_GATEWAY`, `MESH_FALLBACK_POLICY=auto|ask|never`.
- Детект: 3 неудачи подряд за 60 с или 2 подряд TLS/DNS-ошибки → попытка fallback; экспоненциальный backoff; возврат на primary проверяется каждые 5 минут (sticky 10 минут, чтобы не «флапать»).
- Перед fallback — проверка `allow_fallback` тенанта: `auto` (по умолчанию для личных), `ask` (уведомление с кнопкой), `never` (корпоративный).
- Данные residency: при `ask` показываем «Трафик пойдёт через публичный мост вендора; продолжить?».

**Маршрутизация edge.**
- `/d/<device>/mcp` ищет устройство: primary online → primary; иначе fallback online → fallback; иначе `503` с `Retry-After` и страницей статуса.
- Заголовок `X-RHM-Bridge: self-host|public|fallback`; кабинет и трей показывают, где сейчас устройство.
- Если оба офлайн — `503` + `rhm_status` (последний контакт, причина).
- Если клиент уже в сессии, а мост пропал, MCP-ответ содержит структурированную ошибку `bridge_unavailable {reason, fallback_url, reinstall_url, retry_after}`, чтобы агент показал пользователю готовый выбор, а не «не удалось получить ответ от хоста».

**Уведомления.**
- Трей: «Ваш мост недоступен 12 минут. Устройство работает через публичный мост. Вернуть / Переустановить / Подробнее».
- Email/Telegram владельцу (опция), веб-баннер, запись в аудит.
- «Переустановить»: ссылка на `install-bridge.sh --restore` + recovery kit; после восстановления — обратная миграция.

**Метрики.** `bridge_failovers_total`, `time_to_failover`, `fallback_active`, `primary_recovered`; дашборд и алерты.

**Тесты.**
- `iptables DROP` на мост → fallback < 60 с, клиент продолжает работать.
- Просроченный сертификат → fallback + понятная ошибка.
- Возврат primary → sticky, без потери сессии.
- `never` → fallback не происходит, ошибка с инструкцией.
- Оба офлайн → корректный 503 и статус.

**Критерии.**
- При падении self-host устройство остаётся управляемым через публичный мост (если разрешено) без смены URL.
- Пользователь всегда понимает, через какой мост идёт трафик.
- Нет «тихого» fallback без согласия для тенантов с `ask/never`.

**Оценка:** 22 pd. **Зависимости:** E11, edge routing, E4. **Риски:** «флап» между мостами; неожиданный расход трафика вендора; юридические последствия трансграничной передачи.

### E13. E2E-шифрование и защита от недобросовестного хостера (фича 13)

**Цель.** Реализовать модель §5: ключи у пользователя, мост — минимум метаданных, blind-режим для self-host, E2E-шары, tamper-evident аудит.

**Пакет работ.**

| # | Работа | Результат |
| :--- | :--- | :--- |
| 1 | Крипто-библиотека `core/crypto/` (PyNaCl): URK, sealed box, HKDF, AEAD, конверт v2 | Векторы, тесты, версионирование |
| 2 | Хранилище ключей: DPAPI/Keychain/libsecret, fallback — файл 0600 | Ключи не в `agent.env` |
| 3 | Enrollment: создание URK, recovery kit (12 слов + QR), добавление устройства по SAS | Тесты на потерю/восстановление |
| 4 | Шифрование at-rest на мосту: имена, превью, workspace, blobs | Дамп БД без plaintext |
| 5 | E2E-шары: DEK + share key в fragment, WebCrypto-страница | Скачивание без сервера-ключа |
| 6 | Blind-режим: Noise IK edge↔node, MCP на узле, мост-релей | Интеграционный тест: мост не читает JSON-RPC |
| 7 | Blind index для поиска имён | HMAC-поиск, тесты коллизий |
| 8 | Аудит: хеш-цепочка, Merkle root, чекпоинты устройств | Проверка подмены |
| 9 | Аттестация: подпись образов, `/attest`, прозрачный лог версий | `rhm-bridge verify` |
| 10 | Миграция существующих данных: перешифрование при первом входе | Скрипт + откат |
| 11 | Документация: «что видит хостер», DPA-шаблон, trust-страница | Публичная страница |
| 12 | Пентест и bug bounty (крипто-часть) | Отчёт, исправления |

**Инженерные правила.**
- Никакой самодельной криптографии: libsodium/WebCrypto, готовые AEAD, KDF.
- Ключи никогда не логируются; в память — только на время операции; `mlock`/`VirtualLock` где доступно.
- Конверт версионируется; старые версии читаются, новые пишутся только в v2.
- Все крипто-ошибки — fail-closed, с кодом и без деталей в ответе клиенту.
- Тестовые векторы в репозитории; property-based тесты на round-trip и tamper.

**Критерии.**
- В blind-режиме дамп трафика/БД/диска не содержит ни одного plaintext-поля (проверяется тестом-сканером).
- Шара расшифровывается только в браузере; серверный лог не содержит ключ.
- Подмена/удаление аудита обнаруживается чекпоинтом.
- Пентест не находит критичных проблем; высокие — исправлены до GA.

**Оценка:** 50 pd. **Зависимости:** F1, E4, E10, E12; дизайн — в фазе F. **Риски:** сложность и баги (высокий), производительность (Noise/шифрование), UX восстановления ключей.

| `ping`/`pong` | оба | `ts` |

Правила: idempotent `call.id`; `cancel` на неизвестный id игнорируется; при реконнекте узел сообщает активные вызовы; неизвестные фреймы игнорируются (forward-compat).

### E. Глоссарий

| Термин | Значение |
| :--- | :--- |
| **Edge** | Вендорный краевой сервис: TLS, OAuth, стабильные адреса, маршрутизация |
| **Bridge (мост)** | Шлюз, принимающий WS-туннели и MCP-трафик; публичный или self-host |
| **Node (узел)** | Агент на устройстве + MCP-инструменты + локальные настройки |
| **Tenant** | Изолированный контур данных (личный/org) |
| **AgentConnection** | Конкретный облачный агент/клиент с правами и статистикой |
| **Blind relay** | Режим, где мост не видит payload (Noise edge↔device) |
| **Terminating bridge** | Режим, где MCP-сервер на мосту и live-трафик виден оператору |
| **URK/KEK/DEK** | Корневой ключ пользователя / ключ шифрования ключей / ключ данных |
| **Approval** | Запрос подтверждения действия пользователем |
| **Live-сессия** | Одноразовая сессия LiveUSB для онбординга с телефона |
| **Alias** | Стабильный адрес `/d/<device>/mcp`, не зависящий от моста |

**Итог:** план укладывается в 21–23 недели командой 6–7 человек; первые 13 недель закрывают 9 из 13 пунктов (плюс базовый fallback); крипто-модель и федерация — отдельные поздние фазы, спроектированные заранее, чтобы не переделывать транспорт. Главные решения, которые нужны до старта: edge-домен, Google OAuth-брокер, судьба self-signed для мобильных и глубина Docker-изоляции.
