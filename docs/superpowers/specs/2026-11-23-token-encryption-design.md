# Дизайн: шифрование секретов узла «на диске»

- **Дата:** 2026-11-23
- **Статус:** на утверждении
- **Запрос:** «добавь шифрование токена, чтобы он не хранился в открытом виде в `.env` и где-либо ещё»
- **Целевые компоненты:** `core/tokenstore.py` (новый), `core/agent.py`, `core/rekey.py`, `core/menu.py`, `core/server.py`, `core/web_settings.py`, `core/web_share.py`, `install.sh`, `install.ps1`, `ops/windows/agent-watchdog.ps1`, `ops/doctor.ps1`

---

## 1. Зачем

Секрет узла сегодня лежит открытым текстом. Кто прочитал файл — тот получил доступ к туннелю.

**Шлюз уже в порядке** и менять его не нужно: `gateway.py:435` `hash_secret()` хранит только SHA-256 (`token_sha256`, `link_key_sha256`), а `migrate_link_keys()` переписывает legacy-ключи из plaintext в хеш. Проблема целиком на узле.

### 1.1. Где секреты лежат открытым текстом сейчас

| Секрет | Файл | Где пишется |
| :--- | :--- | :--- |
| `MESH_TOKEN`, `MESH_LINK_KEY` | `agent.env` | `install.ps1:1107`, `install.sh:1980` |
| `MESH_TOKEN` | Windows Startup `rhm-agent.vbs` (в `WshShell.Environment("PROCESS")`) | `install.ps1:1150` |
| `MESH_TOKEN` | launchd plist (macOS) | `install.sh:2025`, `core/rekey.py:94` |
| `MESH_TOKEN` | `standalone.env` | `install.sh:1628` |
| токен standalone-сервера | `standalone.token` | `core/server.py:775` |
| токен веб-панели | `web.token` | `core/web_settings.py:35` |
| оба секрета | окружение процесса | `core/agent.py:183` экспортирует все `MESH_*` из файла в `os.environ`, а `core/mcp_tools.py::_child_env` передаёт `dict(os.environ)` **каждой** запускаемой команде |

Последняя строка — самостоятельная утечка: токен попадает в окружение любого `bash_exec`/`run_job`, откуда его видно в `/proc/<pid>/environ` (Linux) и в WMI (Windows), и он утекает в логи любой команды, печатающей своё окружение.

### 1.2. Честная граница возможностей

Шифрование «на диске» на однопользовательской машине защищает от **утечки файлов**: бэкап каталога, скриншот, `cat`, коммит в git, отправка `.env` в чат, `share_file`, синхронизация в облако.

Оно **не защищает** от процесса, уже работающего под той же учётной записью: расшифровать он сможет, потому что агент обязан предъявить токен шлюзу и, значит, держит его в памяти в открытом виде. Обещать больше — врать. Это ограничение фиксируется в документации, а не замалчивается.

## 2. Цели / не-цели

**Цели**

1. Ни один секрет узла не пишется на диск открытым текстом на платформах с ОС-хранилищем (Windows DPAPI, macOS Keychain, Linux libsecret).
2. Там, где ОС-хранилища нет, — Fernet при наличии `cryptography`, иначе честный отказ от обещания: файл остаётся `0600`, а оператор получает громкое предупреждение и точную инструкцию.
3. Существующие установки продолжают работать без переустановки: legacy-plaintext читается, мигрирует автоматически и больше не пишется.
4. Никаких новых **обязательных** зависимостей. Узел остаётся с одной (`websockets`): Windows и macOS обходятся стандартной библиотекой.
5. Ничего не ломается: `rotate`/`rekey`, меню с QR, установщики, watchdog, `doctor`, автообновление, запрет шаринга конфига, редакция логов.

**Не-цели**

- Защита от атакующего, работающего под той же учётной записью ОС.
- Шифрование на шлюзе (там уже только хеши).
- Парольная фраза при старте (см. 3.4, отвергнуто).

**Анти-цели** (что сделало бы работу проваленной, даже если тесты зелёные)

- «Шифрование», ключ от которого лежит рядом с шифротекстом с теми же правами, но **выдаётся** за защиту от копирования каталога.
- Тихое падение в plaintext при отсутствии механизма — с записью в лог «зашифровано».
- Узел, который после неудачной миграции не может подключиться и не говорит почему.
- Секрет, попавший в `argv` (виден в `ps`), в лог, в вывод команды или в окружение дочерних процессов.

## 3. Подходы и выбор

### 3.1. A — только ОС-хранилище (DPAPI / Keychain / libsecret)

`CryptProtectData` через `ctypes` (стандартная библиотека) на Windows; `security` CLI на macOS; `secret-tool` на Linux. Ноль зависимостей, ключ не лежит на диске вообще.

*Минус:* на Termux и «голом» Linux шифрования не будет вовсе — там нет ни одного из хранилищ.

### 3.2. B — Fernet везде + ключ в файле `0600`

Единый формат на всех платформах.

*Минус:* ключ лежит рядом с шифротекстом и с теми же правами. Защищает только от **частичной** утечки — самого `agent.env` без каталога. Плюс `cryptography` становится зависимостью узла, а это ломает принцип «одна зависимость» (на Termux — `pkg install python-cryptography`).

### 3.3. C — гибрид по способностям хоста — **выбран**

Лучшее из A и B, с явным порядком приоритета. Работает везде, на Windows и macOS не приносит ни одной зависимости.

### 3.4. D — парольная фраза (scrypt), ключ не хранится нигде

Сильнее всего против кражи файлов, но узел не поднимется после перезагрузки без человека. Это ломает автозапуск — то, ради чего продукт существует. **Отвергнуто**, в коде не реализуется.

## 4. Архитектура

### 4.1. Один модуль — `core/tokenstore.py`

Единственное место, которое знает, где лежит секрет и как он запечатан. Никакой другой модуль не вызывает шифр напрямую.

```python
SEALED_PREFIX = "mesh1:"

def available() -> list[str]              # механизмы этого хоста, лучший первым
def best() -> str                          # "dpapi" | "keychain" | "libsecret" | "fernet" | "none"
def is_sealed(value: str) -> bool
def seal(secret: str, purpose: str, config_dir: str | None = None) -> str
def unseal(blob: str, purpose: str, config_dir: str | None = None) -> str
def migrate(config_file: str, *, dry_run: bool = False) -> dict
def status(config_file: str) -> dict
```

`purpose` — `token`, `link_key`, `standalone`, `web`. Он же служит именем записи в ОС-хранилище и отделяет один секрет от другого.

### 4.2. Формат

Значение в env-файле:

```
MESH_TOKEN_ENC=mesh1:<механизм>:<полезная нагрузка>
MESH_LINK_KEY_ENC=mesh1:<механизм>:<полезная нагрузка>
```

| механизм | полезная нагрузка | что лежит на диске |
| :--- | :--- | :--- |
| `dpapi` | base64 DPAPI-блока | только шифротекст; ключ выводит ОС из учётной записи |
| `keychain` | `<service>/<purpose>` | только **ссылка**; секрет в связке ключей |
| `libsecret` | `<service>/<purpose>` | только ссылка; секрет в libsecret |
| `fernet` | base64 Fernet-токена | шифротекст; ключ — `token.key` (`0600`) |

Отдельный ключ `*_ENC`, а не перезапись `MESH_TOKEN`: (1) отсутствие plaintext-строки видно глазами и проверяется тестом; (2) `_load_settings` экспортирует все `MESH_*` из файла, и зашифрованный блоб не должен попасть в окружение под именем `MESH_TOKEN` — иначе инструмент, читающий `$MESH_TOKEN`, получит мусор.

### 4.3. Приоритет механизмов

`dpapi` → `keychain` → `libsecret` → `fernet` → `none`.

`none` — не молчаливый откат: `migrate` в этом случае **ничего не переписывает**, пишет в лог и в `status` причину и точную команду, которая включает шифрование на этом хосте.

### 4.4. DPAPI (Windows, stdlib)

`ctypes` → `crypt32.CryptProtectData` / `CryptUnprotectData`, пользовательская область (без `CRYPTPROTECT_LOCAL_MACHINE`), флаг `CRYPTPROTECT_UI_FORBIDDEN`, фиксированная `pOptionalEntropy = b"remote-harness-mcp:v1"` — чтобы блоб нельзя было вскрыть из чужого приложения без знания энтропии. Память освобождается `LocalFree` в `finally`.

Следствия, которые надо принять осознанно: копия `agent.env` на другой машине или под другой учётной записью **не расшифровывается**. Это и есть цель, но сообщение об ошибке должно быть внятным (см. 4.8).

### 4.5. Keychain / libsecret

Секрет кладётся в хранилище целиком, на диске остаётся ссылка:

```
security add-generic-password -U -s remote-harness-mcp -a <purpose> -w <secret>
security find-generic-password -s remote-harness-mcp -a <purpose> -w
```
```
secret-tool store --label=remote-harness-mcp:<purpose> service remote-harness-mcp purpose <purpose>   # секрет на stdin
secret-tool lookup service remote-harness-mcp purpose <purpose>
```

Секрет передаётся на stdin, не в `argv`. Недоступность хранилища (нет D-Bus, заблокирована связка) — ошибка с причиной, а не запись plaintext.

**Имя записи включает отпечаток каталога конфигурации**, а не только `purpose`: `<purpose>@<sha256(config_dir)[:10]>`. Иначе вторая установка узла под тем же пользователем (или тест с `MESH_CONFIG_FILE` во временном каталоге) перезапишет боевую запись в связке ключей — тест менял бы настоящий токен разработчика.

**Оговорка macOS.** `security find-generic-password -w` для записи, созданной другим процессом, может один раз спросить разрешение. Установщик идёт интерактивно (там это нормально), а unattended-агент ответить на диалог не может, поэтому первый `unseal` на macOS должен происходить в установщике или в меню, а не в первый ночной перезапуск. В документации это фиксируется как известное ограничение платформы.

### 4.6. Fernet

`cryptography.fernet.Fernet`; ключ — `<ConfigDir>/token.key`, создаётся при первом использовании с правами `0600` (`os.open(..., 0o600)` + `os.replace`, как это уже делает `core/server.py::ensure_auth_token`). Один ключ обслуживает все `purpose` каталога.

### 4.7. Миграция

`migrate()` читает `agent.env`, находит plaintext `MESH_TOKEN` / `MESH_LINK_KEY` и:

1. запечатывает каждое значение подходящим механизмом;
2. **проверяет результат до записи**: `unseal(sealed) == secret`; при несовпадении файл не трогается, в лог идёт ошибка, поведение остаётся прежним (plaintext);
3. пишет `MESH_TOKEN_ENC` / `MESH_LINK_KEY_ENC`, удаляет plaintext-строки, сохраняя остальные байты файла;
4. заменяет файл атомарно (`os.replace`).

**Резервной копии с plaintext не делается.** Именно она — то, что утекает, и она обесценила бы всю работу. Безопасность замены обеспечивается атомарностью плюс проверкой до записи: файл либо старый, либо новый, полузаписанного состояния не существует.

5. Дополнительно чистит **автозапуск**, иначе апгрейд ничего не даёт: удаляет строку `MESH_TOKEN` из `rhm-agent.vbs` и ключ `<key>MESH_TOKEN</key>` из launchd plist. Агент читает `agent.env` сам, поэтому эти экспорты не нужны; `core/rekey.py` после этого тоже перестаёт их писать.

Когда запускается:

- **при старте агента** — установка лечится сама на ближайшем запуске, без действий оператора;
- **при установке** — установщик пишет запечатанное значение сразу (см. 4.10), plaintext на диск не попадает вообще;
- **вручную** — `python -m core.tokenstore migrate`.

### 4.8. Чтение и отказ

`core/agent.py::_load_settings`:

1. `MESH_TOKEN` в настоящем окружении (например, старый `.vbs` ещё экспортирует) — уважается, как сегодня;
2. иначе `MESH_TOKEN_ENC` из файла — `unseal()`;
3. иначе legacy `MESH_TOKEN` из файла — используется, и запускается миграция.

Неудачная расшифровка (другая машина, потерян `token.key`, сломано ОС-хранилище) — это **не** пустой токен и не бесконечный ретрай. `configuration_error()` получает новый текст: «токен не расшифровывается на этом хосте (механизм X), потому что …; переустановите узел или выполните `python -m core.tokenstore status`». Узел останавливается с причиной — ровно так уже обрабатывается пустой токен.

### 4.9. Секреты больше не попадают в окружение

`_load_settings` перестаёт экспортировать в `os.environ` ключи секретов: `MESH_TOKEN`, `MESH_LINK_KEY` и любые `*_ENC`. Остальные `MESH_*` экспортируются как раньше — на этом держится конфигурация через один файл.

Это осознанное изменение поведения (сейчас `MESH_TOKEN` из файла утекает в каждую дочернюю команду через `_child_env`), поэтому оно покрывается тестом, а не только комментарием.

### 4.10. Установщики

Установщик не реализует шифрование сам — он не пишет plaintext и не изобретает второй формат:

```bash
sealed=$("$PYTHON_BIN" -m core.tokenstore seal --purpose token < <(printf '%s' "$TOKEN"))
printf 'MESH_TOKEN_ENC=%s\n' "$sealed" > "$CONFIG_FILE"
```

```powershell
$sealed = ($AssignedToken | & $pyExeOnly -m core.tokenstore seal --purpose token)
"MESH_TOKEN_ENC=$sealed" | Out-File -FilePath $envFile -Encoding utf8
```

Секрет идёт через stdin, в `argv` не попадает. `MESH_GATEWAY` / `MESH_USER` пишутся как раньше — это не секреты. `MESH_TOKEN` из `rhm-agent.vbs` (`install.ps1:1150`) и из plist (`install.sh:2025`) удаляется.

Если `seal` вернул ошибку (нет механизма), установщик пишет прежний plaintext и **печатает предупреждение** — установка не должна падать из-за недоступного шифрования.

### 4.11. Остальные потребители

### 4.12. CLI

```
python -m core.tokenstore status          [--json] [--config-file PATH]
python -m core.tokenstore migrate         [--dry-run] [--config-file PATH]
python -m core.tokenstore seal            --purpose <token|link_key|standalone|web>   # stdin → stdout
python -m core.tokenstore rotate-key      # перевыпуск token.key с перезапечатыванием (Fernet)
```

**Команды, печатающей секрет в stdout, нет.** Меню показывает ссылку само, внутри процесса; для оператора достаточно того, что токен ротируется через `rekey`. Это осознанно: `argv` и история shell — такие же каналы утечки, как файл.

## 8. Принятые решения (проверить при чтении)

1. Механизм — гибрид C: приоритет `dpapi` → `keychain` → `libsecret` → `fernet` → `none`.
2. Охват — device token, link key, `standalone.token`, `web.token`, `standalone.env`, плюс чистка `.vbs`/plist.
3. Резервной копии с plaintext нет: атомарная замена плюс проверка расшифровки до записи.
4. Секреты больше не экспортируются в `os.environ` и не попадают в окружение дочерних команд.
5. Автомиграция при старте агента — да; установка пишет запечатанное сразу.
6. CLI не печатает секреты.
7. Шлюз не меняется.
8. Имя записи в ОС-хранилище включает отпечаток каталога конфигурации — чтобы тест или вторая установка не затирали боевой секрет.
9. Standalone-сервер больше не получает токен через `nohup env MESH_TOKEN=…`; источник — `standalone.token`.

## 9. Известные ограничения (принимаются сознательно)

| Ограничение | Почему приемлемо |
| :--- | :--- |
| Процесс под той же учётной записью расшифрует секрет | Агент обязан предъявить токен шлюзу; иначе функцию не построить. Граница описана в 1.2 и в документации |
| `agent.env`, скопированный на другую машину/пользователя, не расшифровывается (DPAPI) | Это и есть цель; цена — внятная ошибка вместо тихого отказа (4.8) |
| macOS может один раз спросить доступ к связке ключей | Спрашивается в интерактивном установщике, а не в ночном перезапуске (4.5) |
| Termux без `cryptography` остаётся с plaintext `0600` | Нет ни ОС-хранилища, ни шифра; обещать защиту нельзя — поэтому предупреждение, а не тишина |
| Windows `chmod 0600` не меняет ACL | На Windows защиту даёт DPAPI, а не права файла; каталог и так в профиле пользователя |
