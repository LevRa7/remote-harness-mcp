## 1. Миссия

Ни одна деталь не считается сделанной, пока у неё нет:

1. **владельца** (роль и конкретный агент/человек);
2. **теста** с идентификатором и способом запуска;
3. **доказательства** выполнения (лог, артефакт, скриншот, отчёт);
4. **ревьюера**, который независимо проверил соответствие спецификации и качество.

Принцип: **evidence before claims** (Superpowers, `verification-before-completion`).

## 2. Роли

| Роль | Мандат | Что производит | Право вето |
| :--- | :--- | :--- | :--- |
| **P — Planner / Lead** | Декомпозиция, порядок, зависимости, оценка, ведение матрицы | WBS, план спринта, решения | Блокирует старт задачи без теста и владельца |
| **A — Architect** | Границы сервисов, модель данных, интерфейсы, ADR | ADR, схемы, interface contracts | Блокирует несовместимые интерфейсы |
| **C — Critic / Red Team** | Адversarial-ревью, pre-mortem, поиск противоречий и слепых зон | Отчёт с findings, сценарии отказа | Блокирует релиз при незакрытом Critical |
| **API — API Expert** | HTTP-контракты, коды, идемпотентность, версионирование, OpenAPI | Спецификация API, contract-тесты | Блокирует несовместимое изменение контракта |
| **SEC — Security / Auth** | OIDC, сессии, CSRF, claim, scopes, модель угроз | Threat model, security-тесты, пентест-чеклист | Блокирует релиз при Critical/High |
| **UI — UI/UX Engineer** | Трей, кабинет, состояния, доступность, i18n | Макеты, UI-тесты, UX-приёмка | Блокирует релиз при broken UX |
| **DESK — Desktop Engineer** | Avalonia-трей, автозапуск, control API client, упаковка | Сборка, smoke-тесты, installer | Блокирует Windows-релиз |
| **BE — Backend / Data** | SQLite, миграции, репозитории, usage pipeline | Схема, миграции, тесты данных | Блокирует миграцию без отката |
| **PERF — Optimizer** | Индексы, запросы, SSE/backpressure, память, размер логов | Бенчмарки, профили, лимиты | Блокирует релиз при деградации p95 |
| **QA — Test Architect** | Матрица покрытия, фикстуры, CI-гейты, доказательства | TEST_PLAN, coverage report | Блокирует «done» безevidence |
| **OPS — DevOps / Release** | CI, фича-флаги, деплой, бэкапы, откат | Pipeline, runbook, release checklist | Блокирует деплой без отката |

### 2.2. Параллельный LiveUSB-поток

Отдельный агент (`rescue-agent`, вне основного ростера Wave 1) ведёт Live USB Edition: `core/rescue.py`, `ops/live-usb/*`, `ProjectPlan.md`, `Mistakes.md`, правки `GEMINI.md`. Он не входит в спринты Wave 1 и не блокирует кабинет, но его работа зарегистрирована в WBS как `REV-RESCUE-01…04`.

Правила сосуществования:

- `core/mcp_tools.py` — **общий файл**. Изменения LiveUSB-потока должны быть аддитивными: новые `TOOLS`/`_HANDLERS`/`TOOL_ANNOTATIONS`, без удаления guard'ов `REV-SEC-13` и без изменения `_READ_ONLY_ALLOWED` для `rescue_action`.
- `rescue_info` — read-only, разрешён в `MESH_READ_ONLY`; `rescue_action` — destructive, обязан вызывать `_read_only_active()` и `dry_run=True` по умолчанию.
- `core/rescue.py` и `ops/live-usb/` должны попадать в payload/bootstrap (`install.sh`, `deploy_gateway.sh`), иначе LiveUSB-образ не соберётся.
- Конфликт в `core/mcp_tools.py` решается в пользу security-guard'ов; при сомнении — `arch-01` + `critic-01`.
- У параллельного потока свои тесты (`tests/test_rescue.py`, сборка ISO); его «готово» не закрывает `REV-SEC-13/14` и наоборот.

## 4. Жизненный цикл задачи

```
Planner: WBS-ID + тест + владелец
        ↓
Owner: failing test (Red) → реализация (Green) → self-check
        ↓
Reviewer (не владелец): spec compliance + quality
        ↓
QA: evidence check (команда, вывод, артефакт) + coverage matrix
        ↓
Planner: задача закрыта только при всех зелёных гейтах
```

**Запрещено:**

- закрывать задачу по устному «готово»;
- помечать тест «пройден» без свежего вывода;
- владельцу ревьюить собственную работу;
- добавлять деталь в код без строки в матрице;
- удалять тест без записи в `REVIEW_LOG.md`.

## 5. Definition of Done (для каждой строки матрицы)

> В матрице `Owner` — **исполнитель** (кто пишет код/тест), `Reviewer` — независимый проверяющий. Роль-Accountable из RACI (например, SEC для OIDC) может не совпадать с исполнителем; это не нарушение, если SEC ревьюит и подписывает результат. Владелец-роль — это пул: конкретную задачу выполняет свежий implementer-субагент, но accountable остаётся за строкой матрицы.

- [ ] Код/документ существует по указанному пути.
- [ ] Тест из колонки `Test IDs` существует и запускается командой из `TEST_PLAN.md`.
- [ ] Red-green подтверждён (тест падал до реализации).
- [ ] Свежий вывод теста приложен (файл в `artifacts/` или CI-ссылка).
- [ ] Ревьюер из колонки `Reviewer` поставил `APPROVED` в `REVIEW_LOG.md`.
- [ ] Нет открытых Critical/High по этой строке.
- [ ] Документация/строка changelog обновлена, если поведение видимо пользователю.

## 6. Эскалация

| Ситуация | Кто решает | Срок |
| :--- | :--- | :--- |
| Конфликт интерфейсов | Architect | 1 день |
| Невозможно протестировать | QA + Architect | 1 день |
| Security-находка High | SEC + Planner | немедленно |
| Срыв срока > 20% | Planner | 1 день |
| Неоднозначность требований | Critic + Planner, решение в `REVIEW_LOG.md` | 1 день |

Решение фиксируется как `Ruling: <что> — <почему> — <цена ошибки>`, как требует Superpowers `subagent-driven-development`.

## 8. Протокол коммуникации агентов

1. Ревью-агент **не правит** код и чужие документы; пишет только свой отчёт.
2. Отчёт — файл, а не простыня в чат; в чат возвращается ≤ 12 строк.
3. Каждый finding имеет ID, severity, доказательство (файл:строка), рекомендацию и предложенного владельца.
4. Контроллер (Planner) сводит отчёты, выносит rulings, обновляет матрицу.
5. Повторное ревью — только по изменённым строкам (scoped re-review).
