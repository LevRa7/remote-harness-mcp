# Ревью производительности: Wave 1 «Аккаунт и контроль»

**Роль:** PERF / Optimizer. **Дата:** 2026-11-11. **Статус кода:** реализации нет — ревью плана и существующего кода.
**Область:** SQLite кабинета, usage-агрегаты, SSE/control API, локальный журнал, трей, нагрузочные цели.
**Методика замеров (§2.1):** Windows 11, Ryzen 7 5800H, локальный SSD, Python 3.12.14, SQLite 3.53.1, схема — буквально §5 плана, 1 000 000 строк `usage_daily` (100 устройств × 5 агентов × 10 инструментов × 200 дней). Десктопный SSD быстрее типового VPS (2 vCPU, сетевой диск) в 2–4 раза по I/O, поэтому цифры ниже — **оптимистичная граница**, а не гарантия.

## 1. Вердикт

**READY_WITH_FIXES** — 0 Blocker / 5 Critical / 7 Major / 4 Minor.

План функционально полон, но **в нём нет ни одного измеримого perf-бюджета**: «p95 в бюджете» из релизного чек-листа (v2 §12.D:1494) проверить нечем, потому что бюджета нет ни в Wave 1, ни в v2 (§9.1:1353 задаёт только «100 устройств, 20 параллельных, p95» без чисел, железа и метода). Это делается в Sprint 0 за полдня и без этого нельзя пройти G5.

Три вещи ломают p95 при наивной реализации, хотя чинятся дёшево: SQLite вызывается из async-процесса шлюза без политики потоков (PERF-02); у account-БД нет ретенции и каскадов (PERF-04); дашборд обещает p50/p95, а в схеме только `duration_ms_sum` — метрику физически не из чего посчитать (PERF-05). Отдельно опасен ingest: контракт «cumulative или delta» не зафиксирован, поэтому повторная отправка из offline-очереди может тихо откатить счётчики (PERF-06).

Хорошая новость из замеров: **на заявленном масштабе SQLite не является узким местом** — при 1 млн строк дашборд-запросы по тенанту занимают 0,8–2,8 мс, ингест 2 000 строк одной транзакцией — 15 мс. Переусложнять (Postgres, партиции, materialized views, отдельный сервис агрегации) не нужно; нужно запретить конкретные антипаттерны и зафиксировать бюджеты. Условие снятия: PERF-02…PERF-06 закрыты **до** первой строки `account/db.py` и `core/usage.py` (Sprint 0), иначе после Sprint 2 те же правки стоят в 5–10 раз дороже.

Выводы, которые меняют план: (1) пер-тенантные запросы при 100 устройствах и 1 млн строк **не** требуют ни партиций, ни materialized views; (2) узкое место — не объём, а (а) блокировка loop, (б) ретенция без батчинга, (в) commit на строку, (г) ротация/fsync в горячем пути; (3) `os.replace` на Windows требует явной дисциплины владения файлом.

### 2.2. Пределы масштабирования и минимальные изменения (ответ на вопрос 8)

| Решение в плане | Когда упрётся | Минимальное изменение |
| :--- | :--- | :--- |
| SQLite в процессе шлюза, синхронный доступ | Сразу: один тяжёлый запрос блокирует SSE/релей | `to_thread` + WAL + `busy_timeout`; **не** переезжать на Postgres в Wave 1 |
| `usage_daily` без `day`-индекса и без ретенции | При выходе за 90 дней/1 млн строк | `idx_usage_day`, ночной чанковый purge, бюджет 500 МБ |
| «10k событий/день» без уточнения | Если это **на устройство**: 100 × 10k = 1M агрегатных строк/день → 90 дней ≈ 90M строк ≈ 10–13 ГБ, SQLite перестаёт подходить | Зафиксировать: 10k/день **суммарно** по инсталляции. Если на устройство — ретенция 7 дней + месячный rollup (Wave 2), не в этом релизе |
| p50/p95 из суммы | Невосстановимо после релиза | `duration_ms_max` сейчас; гистограмма — Wave 2 |
| Один процесс шлюза | 1k устройств / 2k SSE-потоков / 10 rps дашборда — ещё влезает; 5k устройств — нет | Не менять; PORT/edge — Wave 3. Метрика: RSS процесса и число потоков в `/health` |
| SSE без ограничения очереди | Один медленный клиент = рост RSS до OOM | Bounded queue + drop/close (PERF-07) |
| Ingest per-request commit | 100 устройств — неважно; 10k устройств — 26 с/день CPU | Уже батч; главное — не commit на строку |
| Чтение всего журнала на сводку каждый час | 190 МБ → 2–3 с CPU/час | Хранить offset+carry, читать хвост с последней позиции |
| Локальный журнал без ротации по времени | 10k/день → 10 МБ за ~5 дней, 5 файлов = ~25 дней | Уже есть 10 МБ × 5; добавить ретенцию по возрасту файла (90 дней) |

Чего **не** делать в Wave 1: Postgres, партиционирование таблиц, materialized views, SQLite-триггеры для агрегации, отдельный сервис агрегации, кэш в Redis, ORM. Всё это добавляет движения частей, не решая ни одного измеренного узкого места.

| L-05 | SSR-страница `/account/usage` | p95 ≤ 300 мс | 90 дней, 100 устройств | то же |
| L-06 | БД | ≤ 500 МБ при 90 днях / 1 млн строк; WAL ≤ 32 МБ | после 3 циклов ретенции размер не растёт | `page_count`×`page_size`, размер `-wal`, `freelist_count` |
| L-07 | Журнал | append p99 ≤ 0,1 мс; сводка 7 дней ≤ 200 мс; 90 дней ≤ 2 с (в фоне) | 50 МБ журнал | микро-бенч + таймер UI-потока |
| L-08 | Трей | **RSS ≤ 120 МБ** (private WS, 10 мин idle), cold start ≤ 3 с, idle CPU ≤ 0,2 %, publish ≤ 100 МБ | чистая Win11, Defender on, без сети | `Get-Process` (WorkingSet + PrivateMemorySize64), `Process.StartTime` → лог «ready», `powercfg /batteryreport` за 1 ч |
| L-09 | Control SSE | ≤ 4 соединения, буфер ≤ 1 МБ, p95 доставки ≤ 500 мс, reconnect ≤ 2 с | 100 реконнектов подряд | тест-клиент + метрики узла |

Правила измерения: p95 — по ≥ 1 000 запросов, 3 прогона, берётся медианный; отчёт p50/p95/p99/max; «холодная» БД и «тёплая» — отдельно; меряется серверное время (middleware) и клиентское (k6), расхождение > 20 % — дефект инструментария. Цифры без стенда, команды и артефакта `bench.json` (VERIFICATION_PROTOCOL §1) не принимаются.

### 2.4. Бенчмарки и регрессия (ответ на вопрос 7)

**В CI на каждый PR (быстро, детерминированно, без флейков по железу):**
1. **CI-1** (`T-PERF-01`) — `EXPLAIN QUERY PLAN` для 5 запросов дашборда: запрещён `SCAN usage_daily`; `SCAN devices` допустим только при ≤100 строках. Дешёво и ловит главный класс регрессий.
2. **CI-2** (`T-PERF-02`) — фикстура 1 млн строк (детерминированный seed) + p95 каждого запроса < 50 мс (запас ×20 к замеру) и e2e `GET /account/api/usage` < 200 мс.
3. **CI-3** (`T-PERF-15`) — ингест: 10k строк/с (замер даёт ~130k/с, порог с запасом), 2000-строчный батч < 100 мс.
4. **CI-4** (`T-PERF-10`) — журнал: 20k append+flush < 200 мс (замер 70 мс), сводка 50 МБ < 3 с, память < 150 МБ.
5. **CI-5** (`T-PERF-07`) — SSE: 100 потоков, 1 000 кадров, дельта RSS < 32 МБ; медленный клиент выселяется.
6. **CI-6** (`T-PERF-12`) — размер publish трея ≤ 100 МБ, cold start ≤ 3 с, RSS ≤ 120 МБ (windows-latest).

**Перед релизом (на эталонном стенде, вручную/ночным job):** L-01…L-09 из §2.3, 8-часовой soak (утечка RSS < 5 %, WAL не растёт), 3 цикла ретенции на 1 млн строк, замер батареи 1 ч, cold start на чистой Win11 с Defender.

**Что считать регрессией (блокирует merge/релиз):** p95 любого эндпоинта +20 % к baseline-коммиту **или** абсолютный > 200 мс; появление `SCAN usage_daily`; RSS шлюза/трея +10 % или превышение бюджета; cold start > 3 с; publish > 100 МБ; append p99 > 0,5 мс; WAL > 32 МБ; рост файла БД после ретенции. Baseline хранится в `tools/bench/baseline.json` и обновляется только осознанным коммитом на эталонном стенде, не на каждом PR.

## 6. Чек-лист готовности домена (что проверю лично перед подписью)

1. `EXPLAIN QUERY PLAN` всех 5 запросов дашборда на фикстуре 1 млн строк — ни одного `SCAN usage_daily` (T-PERF-01), вывод в `artifacts/`.

3. Ретенция: 3 цикла на 1 млн строк, размер файла стабилен, WAL ≤ 32 МБ, job не на loop и не в час пик (T-PERF-05), артефакт `bench.json`.
4. p95-контракт: либо в строке есть данные для p95 (гистограмма/`max`), либо в UI и приёмке написано «среднее/макс»; текст «±1%» исправлен (PERF-05).
5. Ингест: тесты replay/out-of-order/отравления зелёные (T-PERF-03, T-PERF-04); лимиты тела и клампы в коде, а не в документации.
